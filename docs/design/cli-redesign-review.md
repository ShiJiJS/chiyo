# CLI 重设计评审与开发前约定

2026-11-13 · 用户已批准产品范围并授权开发；命令拼写与内部契约由开发 agent 在本文件细化冻结。

本文件供用户确认设计、开发者细化接口，以及后续修改填写说明页共同参考。用户已授权开发 agent 在无其他阻塞时设定 goal 并持续开发，同时由说明页 agent 按本设计修改说明页。下面的命令在实现验收前仍是设计示例，不代表已安装版本支持。

讨论来源：Codex 聊天“配置 Mac 开发环境”（`01a14efb-949c-7fe2-8060-29639b2f5c91`）中用户要求整理的 13 点 CLI 调整，以及说明页聊天中的交叉评审。规格和任务仍以 GitHub Issues 管理；本文件记录设计，不代替任务进度。

## 1. 评审结论

整体方向合理，但原 13 点是改造纲要，还缺少足以决定实现行为的契约。尤其不能只把旧 JSON 包装成子命令，再把旧脚本参数藏起来。

最重要的改变是：Agent 描述业务意图，知予负责具体执行。网页登录时，Agent 应告诉知予“把这份密码填进这个页面的这个框”，不应负责查找 Python、填写脚本或原生辅助程序。

与此同时，用户有意让一个命令行程序使用数据库密码、SSH 密钥等功能仍需保留。浏览器填写与通用程序执行要分别设计；内部填写脚本不再对外暴露，不等于禁止 Agent 指定自己真正要运行的业务程序。

## 3. 聊天、连接与执行设备

建议契约：

- Codex 等受支持宿主由接入适配器提供聊天上下文；业务命令统一，宿主差异留在适配器里。
- 普通终端无法推断聊天时，提供显式选择或建立会话的流程；不能随便采用最近一次聊天。具体命令待冻结。
- 每次调用关联到该聊天已有的私密认证信息。公开聊天 ID 只用于识别来源，不能作为取回权限的凭据。现有 `codex_association.dart` 明确区分二者，重做 CLI 不应删除此边界。
- 并行聊天、子 agent、重开的终端不能通过进程外的单一“当前会话”互相覆盖。主子 agent 是否共享原会话应由宿主适配明确传递。
- 已有聊天绑定原资料库和设备上下文。断网只报原连接失效，不能自动切到本地库、新建申请或继承另一连接的批准。
- 显式切换资料库意味着新的授权上下文，原申请不能移植过去继续使用。
- 状态命令展示：当前资料库、审批位置、执行设备、会话是否有效；不打印私密连接证明。
- hook 可提供真实的聊天结束事件。没有收到事件时，不能把“CLI 进程退出”当作聊天结束。手动结束、过期及撤销仍需明确可用。

开发前需确定：支持哪些宿主、普通终端如何建立上下文、跨进程如何找回它，以及会话结束通知缺失时的处理。

## 4. 填写流程：批准范围与本次目标分开

建议使用两个相互关联的对象：

1. **批准范围**：允许哪份凭据的哪个版本，以哪种填写方式用于指定网页表单和字段，或用于哪个本机应用，多久有效。
2. **本次填写目标**：执行设备、浏览器实例、具体页面和框，或本机焦点控件；在这一次执行中固定。

二者不能混淆。网页批准限定到指定表单和字段，不扩展到同网站其他表单。浏览器实例、页面及表单定位信息都参与执行检查；目标消失时不能猜测替代目标。

建议的目标规则：

| 方式 | 申请及批准必须讲清 | 每次执行必须检查 |
|---|---|---|
| ego 页面 | 浏览器填写方式、页面、指定表单及字段、用途、凭据版本 | 同一设备和浏览器实例、工作区和页面、当前网址、唯一且可编辑的密码框 |
| Chrome 页面 | 同上，并明确选择 Chrome 页面适配 | 浏览器实例、标签页标识、当前网址、元素及适配能力 |
| 前台密码框 | 应用身份、用途、凭据版本；附加网址只能是说明 | 当前前台应用、密码控件、捕获后到发送前焦点是否变化 |

用户已确认网页批准范围为指定表单及字段。网址用于核对表单所在页面，不作为允许整个网站使用密码的范围。申请保存浏览器/页面身份、页面网址、表单或区域定位条件、字段定位条件，以及凭据 ID/版本。

开发须定义表单识别与刷新后的重新核验规则：只在能够确认仍为批准的同一表单和字段时复用；不能确认就拒绝本次操作。跨页面、跨表单、字段变更或重开标签页不能自动沿用旧目标。保留原许可记录不等于可以扩大范围。表单不要求是 HTML form 标签，应用中的登录区域也可有明确定位条件。

本机焦点方式只能核对系统提供的控件和应用信息，不能把它说成对网页来源的证明。页面目标失效时，返回失效原因；不能自动选择另一个同网址标签页、另一个密码框、切换到系统输入或读取原文。

所有方式保持“填写”和“提交登录”分离。结果需区分检查拒绝、文字已发送、能够确认已填写、失败、部分完成和结果未知；按实际观察报告，不统一叫成功。

### 一条建议的调用流程

以下用于审阅交互，不是最终命令合同。正常流程不要求 Agent 额外保存计划 ID：CLI 在提交申请时检查目标并保存计划，后续凭申请编号继续。`R-42` 是申请编号。

```sh
chiyo credentials list --query "项目工作台" --json
chiyo fill request --credential cred-workspace-01 --version 1 \
  --via ego --space 7 --page p1 \
  --url https://workspace.example/login --form '#login' --selector '#password' \
  --purpose "登录项目工作台" --json
# CLI 检查目标、保存计划并提交，返回 R-42；尚未填写

chiyo requests wait R-42 --timeout 60 --json
chiyo fill run --request R-42 --json
# CLI 在发送执行请求前保存操作记录，返回操作编号，例如 O-42
chiyo operations show O-42 --json
```

`O-42` 由 CLI 生成并返回；需要自动化跨进程重试的调用方，也可以显式传入稳定的重试编号。回复连同编号一起丢失时，通过本聊天的操作列表找回原记录，再查询或恢复；不能直接重跑上面的 `fill run` 来猜测是否是同一次。创建申请也需要同样的恢复保证，详见第 6 节。

可额外提供只检查目标而不提交的 `fill prepare`，但不强制所有正常调用先管理一个额外计划编号。最终命令数仍待冻结；提交前检查、批准不执行、执行前重查三件事必须成立。

首次执行使用保存的目标。后续只能在获批的同一表单及字段内复用，执行前仍重查。改变表单或字段需重新申请；旧操作目标不可改写。网页刷新无法确认同一目标时停止，不静默重定位。

## 5. 多凭据与真实使用位置

一份申请可以带多项“凭据＋用途＋使用方式＋目标”。内部可以分配记录编号，但 Agent 不手填 `portal_password` 这类中间别名。

例如，一个业务程序需要：

| 凭据 | 实际用途 |
|---|---|
| 数据库密码 A，第 1 版 | 程序环境变量 `DB_PASSWORD` |
| 服务 Token B，第 2 版 | 程序环境变量 `SERVICE_TOKEN` |

这里的环境变量名是目标程序要求的，不能随着别名一起删除。网页多个框同理：每份凭据明确对应自己的目标框，不能只给凭据列表再让软件猜。

建议按每条获准用途记录批准结果、版本、期限和撤销状态。一项操作声明自己需要的全部凭据；必须全部有效且材料准备成功后才启动，不能启动到一半再发现少了一项。这里只保证启动前的检查，不承诺外部业务动作能回滚。

用户已确认允许部分批准（2026-11-13）：A 获批、B 被拒时，仅依赖 A 的操作可运行；同时需要 A、B 的操作不启动。A 更新或撤销也不应误伤只用 B 的操作。普通录入提案的整体保存规则保持不变。

## 6. 编号、状态、重试与断线

必须分别保存：

- 申请及其审批结果。
- 当前授权是否有效，以及有效的具体范围。
- 每一次操作及其执行结果。

一次执行结束后，授权可能仍可用。`requests show` 可以把三者汇总显示，但不能用一个“已完成”覆盖全部含义。对外优先让 Agent 使用申请 ID 和操作 ID；内部 executionId 可由操作查询结果关联，不要求 Agent为了查询再次拼完整计划。

防重复覆盖两类操作：**提交申请/提案**和**实际执行填写/程序**。记录必须标明类型，不能只给执行阶段防重复。

恢复例子：提交申请回复丢失，找回原提交记录并取得它对应的申请编号；填写回复丢失，找回原执行记录并查询是否已经发送。两种恢复都不新建业务动作。

防重复规则建议：

1. 在第一次网络发送前保存操作 ID 和完整内容；服务端按认证会话＋操作 ID 原子登记。
2. 同一 ID、相同内容只返回原记录；同一 ID、不同内容返回冲突。
3. 网络超时先查询原 ID；状态未知时不重新发送输入、不生成新 ID 掩盖未知结果。
4. 明确的重试引用原 ID，真正再做一次使用新 ID。不能按“参数相同”判定两次调用是同一次业务意图。
5. CLI 自动生成 ID 只解决命名问题。若两个独立进程都执行同一条创建命令，没有共享意图标识，软件无法可靠知道是在重试还是新建。因此必须提供调用方传入幂等键或恢复原操作的明确入口。
6. 本地记录用于恢复，不是批准依据；文件损坏、App 重启或换电脑不能重建有效授权。服务端和执行端已有记录是执行事实的来源。

同一窗口/焦点同时收到两次填写时，建议返回 busy，或在实际执行前重新检查目标；不允许旧焦点操作默默排队后填入新窗口。不同页面是否能并行要由具体适配器明确。

## 7. 输出与退出码

建议把 CLI 调用是否成功与业务状态分别返回。

| 场景 | 期望含义 |
|---|---|
| 申请成功创建，等待审批 | 提交命令成功，申请状态 pending；不是填写成功 |
| 查询成功，读到 denied / expired | 查询命令成功，授权不可用 |
| 等待超时 | 等待命令到达约定期限，返回独立非零码；原申请和批准期限不因此改变 |
| 操作被接受 | 已登记，不等于进程启动、填写完成或登录成功 |
| `operations show` 查询到执行失败或未知 | 查询命令成功，记录中的执行状态为失败或未知；保留原操作 ID |
| 执行命令或等待完成的命令确认执行失败/未知 | 返回相应非零码及明确状态，携带原操作 ID 和下一步查询建议 |

具体数值退出码和 JSON schema 在实施前冻结。机器输出保持一个完整结构；诊断写 stderr；分页、过滤、空列表与未知字段的兼容规则要有例子。不要把私密关联、密码或原始异常中可能含有的秘密写到日志。

## 8. 录入、兼容与能力检查

- 预检使用当前库实际模板，保存模板 ID、版本、摘要与内容；提交时核对是否变化。变化后重新预检，不静默按新模板解释旧内容。
- 新增/修改仍是提案，预检与预览不落库；关联等待状态继续明确区分“已批准”与“已入库”。
- 能力输出按填写方式列出 supported、available、reason。目标是否 ready 是另一次具体检查，doctor 不能承诺任意网页都可填写。
- CLI/App/服务端版本协商须覆盖新目标批准与多凭据语义。旧服务不支持时明确失败，不降级成任意脚本启动，也不拆成多份申请绕开用户看到的批准范围。
- 旧 `info-codex` 是否过渡保留及何时移除需要确认。新旧入口可以共享实现，但旧授权保留原语义，不能自动升级到更宽范围。

## 10. 验收场景与后续说明页依据

## 12. 2026-11-13 用户补充与范围澄清

用户明确允许多凭据部分批准。用户同时询问 Chrome 是否已有标签页＋选择器能力，并提出“实际应指定表单并填入对应表单”的理解。

- 每一次填写必须定位具体浏览器、页面、表单/区域及字段；批准网站范围也不能省去这一步。
- 网站级批准讨论的是能否把同一许可复用于该网站的其他表单，不是让软件在整个网站随意寻找框。

## 14. 第一轮实施接口（2026-11-13）

以下固定命令名和字段含义；规格和实现状态由 [GitHub #143](https://github.com/ShiJiJS/chiyo/issues/143) 及其测试回执记录，文中的调用例子不代表旧安装包已支持。产品实现位于 `codex/cli-redesign`，教学 HTML 由说明页会话独立维护。

### 对外命令

- `chiyo credentials list --query TEXT [--directory ID] [--json]`：查询公开凭据元数据。
- `chiyo connection show [--json]`：显示本次私密上下文绑定的库、模式、审批位置与执行设备。
- `chiyo access request --item ITEM_ID --field FIELD_ID --purpose TEXT [--operation ID] [--json]`：单字段申请直接用参数；多个字段使用 `--input FILE`，业务文件只包含 `{"fields":[{"itemId":"...","fieldId":"..."}]}`。不要求填写内部协议 JSON。
- `chiyo browsers list --via chrome --browser URL [--json]`：只连接调用方指定的 Chrome CDP HTTP(S) 入口并列出页面；不扫描端口或读取浏览器用户资料。第一轮仅接受本机回环地址。`--browser` 表示浏览器实例的连接地址，不是网页网址；连接后固定其 browser WebSocket 身份。
- `chiyo fill request --credential ID [--version N] --via ego --space N --page p1 --url URL --form CSS --selector CSS --purpose TEXT [--operation ID] [--json]`。
- `chiyo fill request --credential ID [--version N] --via chrome --browser http://127.0.0.1:9222 --tab TARGET_ID --url URL --form CSS --selector CSS --purpose TEXT [--operation ID] [--json]`。
- `chiyo fill request --credential ID [--version N] --via focus --purpose TEXT [--operation ID] [--json]`：捕获实际前台应用身份并供审批；不接受网页表单参数，不把应用信息当成网站证明。
- 多凭据填写使用 `chiyo fill request --input FILE`；文件中的每项直接包含 `credentialId`、可选版本和真实目标字段，不含中间别名。文件只表达业务计划，不包含内部程序路径。
- `chiyo requests list [--kind KIND] [--status STATE] [--json]`、`chiyo requests show ID [--json]`、`chiyo requests wait ID --timeout SECONDS [--json]`：只处理当前已认证聊天的记录。
- `chiyo fill run --request ID [--item ITEM_ID ...] [--operation ID] [--json]`：使用已保存且获批的填写计划，创建一次新操作；首次发送前持久保存操作编号。省略 `--item` 表示执行完整计划，所有依赖均须获准；部分批准时，可根据返回的条目 ID 选择独立可执行的部分。条目 ID 由软件生成，与要求 Agent 手工起别名不同。输入的 `--operation` 仅供调用方明确同一业务意图，不根据参数相似度猜测重试。
- `chiyo operations list [--request ID] [--json]`、`chiyo operations show ID [--json]`、`chiyo operations retry ID [--json]`：恢复原记录，不创建新的业务意图；结果不确定时只查原结果，不重放输入。
- `chiyo exec request --input FILE`、`chiyo exec run --request ID [--operation ID]`：明确运行用户业务程序的独立入口，保留标准输入、环境变量及受管文件接收。它不作为内置网页填写的替代协议。
- `chiyo templates list/show/examples`、`chiyo proposals check/submit/show`、`chiyo doctor` 及各级 `--help` 沿同一风格提供；复杂内容使用 `--input` 或专用数据 stdin，秘密材料不进入普通参数。

### 表单和目标核对

`--form` 必须唯一选中页面主文档中的一个登录区域；可以是 HTML form，也可以是明确的容器。`--selector` 是在该区域内部解析的字段选择器，须唯一匹配；不因主文档出现同名元素而改选其他框。首轮秘密字段支持可见、可编辑的 HTML 密码输入框；普通账号字段由返回的已获准账号和普通输入能力处理，不为使用方便读取密码原文。

申请冻结：设备、提供者（ego/chrome/focus）、浏览器实例、页面标识、完整页面 URL、区域与字段选择器、区域结构指纹、凭据 ID/版本。指纹只取定位和表单结构属性，不读输入框值。刷新后只在同一页面标识、URL 与区域/字段结构仍吻合时复用；页面关闭、跨页面导航、结构变更或无法证明一致时拒绝本次执行。执行前再次检查；发送后发现目标变化则标记结果未知，不改道。

Chrome 需要浏览器实际提供控制入口；CLI 通过 `doctor` 和目标预检说明是否可用，不自动更改 Chrome 设置、打开默认用户资料或启动替代实例。真实浏览器验收可使用独立、受控的合成测试实例，须与日常浏览器的支持说明区分。

### 上下文、编号与结果

业务命令与宿主接入分开。宿主已提供有效私密关联时自动复用；Codex 原关联可通过受保护环境或独立 stdin 传给统一入口，业务参数不再使用协议 JSON。普通终端显式创建新的、初始未授权的私有上下文。缺少可靠上下文时明确报告，不从公开聊天 ID、最近会话或其他资料库找回许可。CLI 不把一次进程退出解释成聊天结束。

宿主通过本聊天独立的 `CHIYO_CONTEXT` 环境值提供私有文件引用，或显式使用根选项 `--context-stdin` 从独立 stdin 提供引用；业务 JSON 的 stdin 与此互斥。既有 Codex 私有引用仍由原宿主校验，不因统一命令而放开聊天核对。普通终端使用 `chiyo chat start --agent NAME --id CHAT_ID --label LABEL --context-out FILE [--connection AGENT_PROFILE]` 建立无初始许可的新聊天。CLI 将认证信息写入专用私有文件，不在正常输出里返回会话证明、结束证明或私有路径；调用方已知道自己指定的输出文件，并在该终端设置 `CHIYO_CONTEXT`。不能覆盖已有聊天文件，不能修改一般目录的访问权限来强行保存。连接配置在建立聊天时固定，后续 App 模式切换不改变该聊天的审批位置。`chat show/end` 显式查看或结束原聊天；普通终端没有真实聊天结束 hook 时使用结束命令，不把每条业务命令退出当作聊天结束。

公开运行描述升级到 `schemaVersion: 2`，`cliPath` 指向 `chiyo`，`legacyCliPath` 仅记录兼容程序，`hookPath` 和 `workerPath` 保持各自职责；四份二进制和随包说明均记录摘要。描述只含公开位置和版本核对资料，不含聊天证明或连接密码。完整新包可以原位升级 schema1 描述；缺少新入口时拒绝更新，不退回旧入口假装完成。重复登记相同内容不重新写盘；替换使用同卷原子发布，失败保留旧描述。准备独立运行包时一并复制 `chiyo`，新说明的主要调用入口指向它。

`--operation` 对申请提交和执行都有效。同编号同内容查询或返回原事实，改内容报冲突。CLI 先保存恢复记录再发送；号码丢失时可在本聊天操作列表找回。新建操作与恢复旧操作使用不同命令。一个申请可有多个操作，批准状态、每项授权状态、操作状态分别返回。

CLI 的恢复记录按原私密聊天及连接隔离，只保存不含材料的业务意图；录入原文使用冻结来源引用，不复制密码材料。每条上限100 KiB，每个聊天上限1000条、合计8 MiB；占满时不自动删除尚待核对的记录，也不在保存失败后继续提交。`operations list` 的 `records` 保持服务端分页，另附同范围分页的 `localIntents`。后者的 `state: unconfirmed` 仅表示本机保留了意图，不代表服务器收到、用户已批准或曾经执行。`operations show` 优先查询服务器；明确未找到且有本机意图时才返回该未确认记录。幂等的申请提交可用原内容、原编号恢复；填写执行恢复只查原结果，不重新输入。申请提交的回复丢失也使用退出码7并保留原操作编号。

JSON 输出的公共外层固定为 `schemaVersion: 1`、`ok`、`data`，失败时带 `error.code/message` 与可用的原操作编号；普通命令与 `--json` 具有相同语义。提交待审和查询到已拒绝均可为 `ok:true`。退出码：0 为命令按约定成功；2 为输入或用法错误；3 为连接/上下文不可用；4 为执行被拒绝或授权不足；5 为执行失败；6 为等待超时；7 为执行结果未知；8 为版本/操作内容冲突。查询到业务失败仍返回 0；只有执行或等待完成的命令按其约定返回相应失败码。

新协议必须显式协商多凭据、表单约束和提交防重复能力。旧授权按原规则解释，不能静默扩大成新范围。正常录入提案依旧整体保存；使用申请允许逐项批准。每次操作在启动前核对所需项全部有效并准备齐材料，外部业务行为不提供事务回滚承诺。

## 16. 多项使用申请与持久记录

多项使用申请保存一份原始计划，内部为每条“凭据版本＋实际目标”分配条目 ID。相同凭据可用于不同目标；完全重复的条目拒绝。申请时固定解析出的凭据版本及当时的使用状态，后续密码更新、停用或撤销不能让旧批准自然转用新密码。网页目标和本机前台应用分别解析，不能用本机应用身份替代网页表单范围。

一次批准决定中，选中的条目获准，其他条目拒绝；每条保留自己的决定与固定到期时间。撤销 B 不撤销独立的 A。执行完整计划时必须全部获准且材料准备齐全；只执行 A 时，显式选择软件返回的 A 条目 ID。普通录入提案仍然整体保存。

申请提交和每次执行都在原聊天及设备下登记稳定操作编号。同编号同内容返回原记录，同编号换申请或改变所选条目报冲突。原操作的重复查询不再签发材料领取证明。同一页面或本机输入焦点已有活动操作时返回 busy，不把输入排队到未知的未来窗口。原输入结果未知或只完成部分时，不允许用新编号绕过核对继续填写。

材料领取属于 App 的内部执行通道：先核对全部目标和批准范围，完整准备后才发布材料，领取事实写入存储后才能交给填写程序。每次发送前再次核对当前批准。这个过程使用的短期证明只约束本次执行，不缩短用户已经批准的两小时等使用期限；证明不进入普通 CLI 输出、公开记录或可移植备份。

批准状态、每项当前是否可用、单次执行结果分别记录。“结果未知”不意味着程序已停止或输入没有发生。普通服务器重启保留原聊天和设备下仍有效的批准；未取得确定回执的旧输入标为未知，不恢复其一次性输入证明。可移植备份只保留已作出决定的历史和操作结果，丢弃待审工作、活动证明及可恢复许可；恢复后旧批准不可使用。

存储采用按条更新的加密记录，避免每次操作重写全部历史。首次保留新事实时才要求资料库格式 65；含新历史的备份使用格式 28，旧资料库和不含新事实的备份保持原兼容规则。上述新协议仍须完成 App、服务端、执行 Host 和安装版本协商后才能对外启用；规则的记录不能作为完整功能已经交付的证明。

## 17. 动态提案预检与来源固定

`chiyo proposals check --kind import|update|delete --input FILE|- --json` 检查业务内容，返回 `checkId`；`chiyo proposals submit --kind KIND --check CHECK_ID --input FILE|- [--operation ID] --json` 提交同一份已检查的内容。新增业务 JSON 只包含 `title`、`purpose`、`items`；修改使用 `update`，删除使用 `itemId`、`baseVersion` 和可选 `fieldId`。聊天来源由私密上下文补齐，操作编号使用参数；不要求填写内部 command、协议或会话认证字段。新增每项必须明确动态模板 ID。`templates show/examples` 提供对应业务 JSON 示例以及检查、提交命令。

检查复用正式保存的模板编译和提案验证，不创建提案、不保存资料、不上传普通附件。普通附件仅向预检端点发送文件名、类型、长度和摘要；凭据仍使用专门材料通道，预检不把材料写入记录或返回。修改、删除的现有资料及版本核对继续在用户审批时完成，预检不能变成未经批准探查私有资料的接口。

CLI 在本聊天及原资料库的私有目录固定业务内容摘要、附件/凭据文件摘要与长度，以及所用模板的完整公开定义、ID、版本和摘要；不复制来源正文或凭据材料。每份检查最多 2 MiB，同一聊天的全部本地记录仍最多 1000 份、合计 8 MiB，普通操作记录保持 100 KiB 上限；超限明确停止，不删除尚未核对的旧操作。Windows 继续使用用户 DPAPI 与私有 ACL。检查记录不会混入“已提交操作”列表。

提交前重新查询模板并核对内容和文件；实际上传边界还会核对即将发送的字节。任何变化要求重新检查，不悄悄按新模板解释或上传新文件。文件的相对路径以业务 JSON 所在目录解析；标准输入以当前工作目录解析。提交操作在第一次业务写入前保存编号、检查引用及来源文件位置，回复丢失后按原编号查回原提案。来自标准输入的内容不另存副本；服务端尚无记录时，需要调用方重新提供同一内容和原编号，不能凭摘要重建正文。检查不保证后续批准一定成功：模板、资料版本、关联与完整材料在提交和整体保存时仍须重新核对。

## 18. 原文读取命令的提交与恢复

`chiyo credentials reveal request --credential ID [--version N] --purpose TEXT --reason TEXT [--operation ID] --json` 单独申请读取字符串凭据。省略版本时，从当前可见凭据目录解析并固定版本；同一提交编号的后续恢复使用原版本，不因密码更新改用新版。理由必须说明为什么直接填写或程序接收无法完成。普通填写批准不包含原文读取许可。

服务端按原聊天的私密绑定与操作编号保存创建摘要；同编号同内容返回原申请和原期限，改内容返回冲突。此项私有恢复事实只进入加密本机/服务器存储，不进入一般请求 JSON、公开目录或可移植备份。首次保存此事实要求资料库格式 66，旧记录及无此事实的备份格式保持兼容；备份恢复不恢复聊天许可。既有原文读取在服务重开后失效的规则不扩大为自动恢复批准，只能查询回原申请及读取历史。

`chiyo credentials reveal read --request ID [--operation ID] --json` 仅在单独批准仍有效时返回密码原文，并明确说明它会进入当前聊天。读取操作先保存编号，再由服务端持久记录后返回。若回复丢失，`operations show/retry` 或同编号 read 只核对原记录，不再次返回密码。普通查询读取到 completed 表示服务器记录过读取，不能证明 Agent 收到了原文。确需再读，使用新的操作编号并再次核对原批准；不得把新编号当作自动恢复方式。资料原文不会存入本地操作文件。
