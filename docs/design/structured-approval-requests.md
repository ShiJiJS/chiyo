# 申请的标题、概要与执行参数

凭据申请将任务标题、用途概要和实际执行参数分开：简短标题识别任务，一两句概要解释用途，程序、凭据和命令独立展示。Flutter 界面与跨平台 CLI 采用同一套字段，不改系统权限或实际执行/批准边界。对应任务：[GitHub #147](https://github.com/ShiJiJS/chiyo/issues/147)。

## 采用的结构

- 程序、SSH 登录/认证、网页与原生填写的凭据申请支持 `title`（1–80 字、单行）与 `summary`（1–600 字）。不从长脚本推断用途；说明不构成只读保证。
- `launch`、SSH `target`、填写 `items` 沿用已有实际参数和凭据引用。程序身份、设备、接收位置、版本、批准期限及每次执行前校验照旧。
- 新增离线 `chiyo exec template`、`chiyo ssh template`、`chiyo fill template`；`--out` 写入新的 JSON 文件，拒绝覆盖原文件；无须连接 App、建立聊天或读取 stdin。程序模板支持 env/stdin/file，填写支持 ego/chrome/native。
- `request --input` 可直接接收填写后的模板。普通参数也支持 `--title` 与 `--summary`；旧 `--purpose` 和旧 JSON 仍有效。混用说明别名或文件/单项参数时明确报错。
- 为兼容既有存储，概要的内部持久字段仍为 `purpose`，只新增可选 `title`，不重复保存同一段概要。公开新输入为 title/summary；旧记录的摘要和指纹保持不变。
- 新字段随不可变提交摘要、审批快照、授权历史、同步及备份保留。旧服务端通过 `request-presentation.v1` 能力检查拒绝新申请，不能静默丢标题。含新标题时按内容触发资料库格式 72 / 备份内容格式 33，旧资料不被整体重写。
- 历史没有标题时，按实际申请类型/程序/凭据生成短标题，保留原 purpose，不把旧说明再重复作大标题。

## 原型到工程的对应

| 原型 | 现有工程 | 实现方式 |
| --- | --- | --- |
| 紫色、白纸底、灰色侧栏 | UiPalette | 用现成的 |
| 标题/概要/来源与状态 | libraryText、libraryHeading、LibraryPill | 新建共享标题组件，按钮与文字用现成的 |
| 程序、凭据、接收位置三列 | ProgramPlan、CredentialBindingCard | 现成组件调整布局，窄区域按内容换行 |
| 批准范围 | 既有申请边界说明、期限及范围选择 | 用现成语义，复用为历史摘要，保留部分批准和撤销 |
| 完整程序计划 | ApprovalExactDetails | 现成的加边界样式，默认收起；参数和脚本仍可完整选择/滚动 |
| 执行结果 | ApprovalExecutions | 用现成的状态、只读刷新与原操作核对，缩小冗余排版 |
| 搜索/翻页/审批操作 | 现有控制器与 Desktop 控件 | 用现成的，不新增依赖或重写交互 |

## 验证范围

离线模板生成与不覆盖文件；新旧输入及字段错误；请求—批准—历史的标题保留与不可变摘要；重开、同步、备份恢复不丢字段；既有执行批准边界保持；Flutter 申请和历史的真实组件画面及必要折叠交互。仅使用自制数据和隔离测试库，不触碰日常资料，不启动第三方程序。
