## 2026-11-01：恢复数据与原操作回执原子提交

新增 `inspectRestore`、`restoreWithReceipt` 与只读 `restoreOperationReceipt`。
预览绑定当前接收库对象、状态版本、不透明归档身份和加密文件摘要；认证检查前后及
提交前重新核对归档，提交事务内再次核对接收库版本、空库要求和实际恢复计数。
释放预览、重开/换接收库、文件变化或保留策略导致计数变化都不能沿用原预览恢复。
沿用原有 SQLCipher 解密/认证和附件读取，没有另写备份格式或加密算法。

恢复数据、旧表单暂存清除、旧操作失效、版本推进和本次成功回执在同一事务提交；
模型缓存只在提交后发布。回执写入失败一起回滚，不留下“资料已换、结果却未登记”。
本次回执在旧操作失效后写入，之后再次恢复则使它失效。同编号同意图返回原结果，
不同意图冲突；原归档删除或数据库重开也不触发重放。回执只含操作/资源身份、摘要、
版本、文件名及实际计数，无原始路径、恢复密钥或资料正文，不进入可移植备份。
继续使用schema38/39本机表，恢复回执私有payload为format3。

Owner新增 `restoreLibraryOnce`：在同一Owner写锁下先只读核对准确意图的持久回执，
只有确认未提交的新恢复才进入原恢复屏障、清除旧运行关联并推进库代次。
已成功后的核对不会再次清除新建会话/授权；未知或冲突必须报错，不能当作未执行。
调用方仍需验证回执匹配完整命令，不能直接把任意回执视为当前提交成功。
恢复期间排队的旧表单继续按库代次拒绝；整页Host重绑仍待实际适配器接入。

检查见[证据](evidence/zhiyu-round09/m05-restore-journal.json)：storage全套271项通过、
19项平台/外部条件跳过，其中新增恢复9项覆盖旧format7、附件、事务故障、重开核对、
预览失效、计数变化、竞争和日志排除；Owner备份/库代次14项、desktop相关13项通过，
storage/core静态分析通过。首次全套因默认 `/var` 临时目录别名触发旧fixture清理与AOT
路径保护报44项runner错误；改用 `TMPDIR=/private/tmp` 后全套通过，未放宽保护或改产品逻辑。
那次遗留的46个准确合成临时目录已按创建时间、规范路径及进程占用核对后清理，
共718810517字节。测试结果有重叠，不累加为独立覆盖数。

新增回执的重开测试为同进程重建数据库/Owner；全套既有AOT检查不代表新回执已完成
独立正式App进程验收。下一步仍为生成文件前的暂存租约、原生目录生命周期、换库后的
旧清理记录、未知操作的界面重开恢复，以及 `WorkspaceBackupSource`/Host联合接入。
本轮未替换候选/正式安装/预览，无个人库、Keychain、CUA、原生面板、Windows操作或新App/dSYM。
当前候选仍1443d358，#74保持OPEN，仍不是#73换包的新前置。

## 2026-11-01：文件发布接入 SQLCipher 原操作日志

新增 `prepareOutputOperation`、`publishOutputOperation`、`reconcileOutputOperation`
及独立清理接口，覆盖恢复密钥另存和加密归档导出。准备记录先核对现有恢复密钥或
认证解密实际备份，完整分类计数从实际归档得到；路径/文件身份只存本机加密日志，
对外回执只含操作身份、摘要、版本、动作、显示文件名及计数，没有密钥或原始路径。
沿用schema38/39的本机操作表，私有payload为format2；没有新增可移植备份内容格式。

状态区分已准备、正在发布、成功及确认未发布。发布前必须先提交“正在发布”，
且只有本进程新登记的意图可尝试一次发布；重开或重复调用只能核对，不能重新发布。
已准备阶段中断可确认未发布；正在发布阶段若原文件身份不能匹配，保持未知，
不能因缺失/相同字节的其他文件推断原操作未提交。确认匹配后重新核对文件及目录
同步结果，再将成功回执和“恢复密钥已另存”一起提交。数据库提交失败会回滚该标记，
保留暂存原件供之后核对。准备、终态和清理推进状态版本，已完成回执不因后来清理改变。

清理与成功分开：只处理登记的暂存名字，失败保留待清理状态；成功回执不会因此
变成失败，也不依赖用户日后是否保留输出。旧意图与本机日志不进备份；恢复库后
旧意图失效，不能用于重新写出文件。现有库的恢复密钥与新备份不匹配时不能标为已另存。

检查：[证据](evidence/zhiyu-round09/m05-output-journal.json)。storage全套261项通过、
19项平台/外部旧探针条件跳过；之后补充发布前事务失败检查，最终输出日志13项通过，
静态分析通过；desktop相关13项通过。覆盖发布成功但成功回执提交失败、重开核对、
确定冲突、准备中断、未知状态不重放、清理失败、意图/版本竞争、错误密钥、损坏日志、
恢复失效及实际加密备份导出/恢复。各次有重叠，不累加覆盖数。重开为同进程重建
数据库与Owner对象，不能借上一节的独立原生驱动测试称为生产日志跨进程验收。

下一步仍需生产适配器：生成文件前的暂存租约登记、原生面板同卷目录生命周期、
恢复操作回执及成功换库后的旧清理记录处理、未知操作的界面重开恢复、
`WorkspaceBackupSource`/Host组合及联合检查。该层要求调用方持有Owner备份屏障，
不把当前存储接口当作已挂入App。当前候选/正式安装/预览未变，没有新App/dSYM、
个人资料、Keychain、CUA、原生文件面板或Windows操作；#74仍OPEN。

## 2026-11-01：可跨进程核对的 Mac 文件发布

新增 `MacBackupPublicationFiles`。在用户选定目标所在卷的私有暂存目录准备文件，
记录原件及两侧目录的内核身份、长度和摘要；先保留原件，再创建发布用硬链接，
用 `renameatx_np(RENAME_EXCL)` 发布到目标。目标存在时拒绝，不回退覆盖或复制。
原件保持到成功回执持久提交后再清理，因而进程重开可以确认目标是否就是本次原件。

恢复密钥暂存写入采用独占创建和0600权限，私有目录要求0700且没有扩展ACL。
目录、文件和清理使用描述符相对操作，拒绝符号链接、目录/文件替换及准备前已有
其他硬链接的源文件；内容或权限模式变化也拒绝发布，防止恢复密钥权限扩大后仍被发布。清理只处理登记的暂存原件和发布用名字，
未知对象保留，不递归清理，更不删除用户保存的输出。输出名字、目录和文件身份等
属于私有日志内容，不进入页面资源或Agent响应，异常不带私有路径或材料正文。

核对返回匹配、缺失或不同对象的观察，**缺失或替换不能证明原操作未发布**。
核对本身不会重放发布，持久成功回执仍应独立于后来文件是否存在。

16项实际Mac文件检查和storage静态分析通过，详见
[证据](evidence/zhiyu-round09/m05-file-publication.json)。包括0600、已有相同字节输出
不冒充成功、不覆盖、重复发布、源内容/文件/两侧目录替换、符号链接/FIFO、未知暂存
对象、权限/ACL、无效私有记录及预先存在的硬链接。两个独立Dart进程验证发布后无
回执退出、下一进程只核对并清理，输出修改时间保持。另用真实SQLCipher导出，
经该发布层后关闭源库、清理原件，仍能在独立空库恢复合成资料。

这完成文件发布驱动，**尚未接入生产SQLCipher操作日志、WorkspaceBackupSource或Host**。
独立进程检查的日志是测试fixture，不冒充生产持久回执。下一步将准备记录先落库，
再写出/发布并保存结果，处理中断状态和清理待办，然后接设置页面及恢复换库重绑。
没有系统文件面板、正式沙箱Release、Keychain、个人库、CUA或Windows验收，没有新App/dSYM。
临时文件由测试清理，候选仍1443d358。上轮7ec44797推送已成功；#74继续OPEN。

## 2026-10-30：密钥创建与原操作回执原子提交

新增 `InformationBackups.enableWithReceipt`：操作编号、完整命令摘要和期望版本先核对，
恢复密钥创建、状态版本推进和不含密钥的回执在同一个 SQLCipher 事务提交。
响应丢失后按原编号查询，跨重开仍可找到；同编号同意图返回原回执，不轮换密钥，
同编号不同意图或陈旧版本拒绝。已有密钥继续使用，不因为新版接入重置它。
非法参数及损坏回执明确报错，不能当作未执行而重放。

本机 schema 为普通库38、可移植填充库39，旧36/37升级保留密钥及格式边界。
新操作表与本机版本不进入可移植备份，没有新增备份内容格式。成功恢复在同一
事务中失效接收库旧回执并推进版本，保留本机已有恢复密钥；失败恢复一起回滚。
旧版创建密钥/另存入口也推进同一状态版本，避免新界面继续使用旧观察。

检查结果见 [机器可读记录](evidence/zhiyu-round09/m05-key-operations.json)：

- storage 全套231项通过、19项因平台/外部旧读者条件跳过；静态分析通过。
- 随后补强非法参数及损坏回执检查，最终密钥操作定向10项通过、静态分析再次通过。
  覆盖事务故障回滚、并发版本竞争、重开去重、备份排除、恢复成功失效/失败回滚和36/37升级。
- desktop 四个相关测试文件13项通过：文件选择资源、Owner组合和原备份控件。
  首次命令误写不存在的 `backup_flow_test.dart`，修正为 `backup_flow_widget_test.dart` 后通过。
  原生通道为模拟，不是系统文件面板验收；各次结果有重叠，不相加为独立覆盖数。

本段只完成创建密钥的持久回执。文件另存/导出发布与数据库回执之间的失败核对、
恢复操作回执、实际 `WorkspaceBackupSource`、正式Host/picker组合和恢复后的重绑仍待实现。
不能把普通文件存在当作成功，也不能将未来的文件操作直接包进数据库事务冒充原子提交。
当前候选仍为1443d358，尚未包含本段结构升级；正式安装和预览均未替换。
没有个人资料、系统钥匙串、computer use、新App/dSYM或Windows操作，#74仍OPEN。

## 2026-10-30：原生文件选择的Owner资源边界

新增 `OwnerWorkspaceBackupFiles`，复用 `NativeBackupFilePicker` 四类原生选择方法。
页面只接收随机不透明ID、显示文件名、种类和版本，路径留在Owner适配器内部。
每种选择保留一个当前对象；取消/失败保留先前选择，重新选择使旧对象不可解析。
解析校验完整资源和用途，不能通过猜ID、更换名字/版本或混用输入/输出获得路径。

绑定OwnerLibraryScope：选择前后均核对服务及原库代次，恢复成功或关闭后到达的
选择不能应用到新库。并发文件面板拒绝，原生异常仅映射为通用错误，不把包含私有
路径的系统错误直接传到页面。没有读取备份/密钥正文，没有发布文件或恢复资料。

`owner_workspace_backup_files_test.dart` 4项通过，覆盖中文空格同名文件/取消/重选、
篡改资源/种类混用、换库和关闭期间迟到、并发/原生异常/相对路径，以及实际
NativeBackupFilePicker的四种MethodChannel调用映射。输入为模拟原生通道，不是
真实NSOpenPanel/NSSavePanel验收。desktop静态分析通过；首次编译补齐OwnerInbox
扩展导入及测试用空MemoryInformationRepository，不涉及产品存储结构修改。

下一步：持久操作意图/结果和文件发布失败核对、实际WorkspaceBackupSource、
OwnerWorkspaceHost/picker组合、恢复后重绑与独立进程往返。本轮模块尚未挂入正式
组合，现有备份页继续如实显示未接入；不把文件选择边界称为备份功能完成。
