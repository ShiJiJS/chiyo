# 真实资料中的登录凭据未整理到可用状态

用户发现服务器和应用页找不到登录凭据。核对原始配置、上一轮完成的加密备份和当前正常App，确认原资料确实含私钥、密码及Token，不能将问题归因为用户未提供。

发现两个问题：

1. **凭据关联没有在对应服务器/应用页显示。** 16个服务器/应用中，10个有凭据从凭据库指向它们，但信息本身的凭据列表全部为空。正常App的服务器页实际显示“尚未关联”。真实工作区只显示信息布局中的关联，没有像示例工作区那样合并凭据库的反向关系。凭据已经存在，页面却让用户误以为没有。
2. **全部16项都录成了凭据文件。** 私钥和会话文件适合这种方式，但含账号密码或Token的JSON和运维说明也只是整份保管，没有形成清楚、可直接选择的账号密码/Token项；部分只关联到说明文档，没有直接关联所属应用。文件原文完整不能代表登录资料整理完成。需要补强Skill与动态模板的选择说明，并用不提示答案的新会话复验；不新增CLI提取JSON字段的专用协议。

部分源资料明确没有提供或记录登录密码。此类要明确说明缺什么，按既定规则准备主人补填或暂缓，不能虚构密码，也不能和“已有凭据却未显示”混为一谈。原配置中的初始密码也不能当成已经验证有效的当前密码。

最初为只读检查。独立恢复的临时数据库已关闭清理；正常资料、原infos、程序及钥匙串没有修改。既有46份来源原件和备份一致性的结论仍成立；此前将其归纳为凭据录入验收全部完成不充分，#78/#79需重新处理。普通附件版本保留的#80结论不因此改变。

后续检查应包括：从服务器或应用详情找到正确凭据；在凭据详情看到正确归属；密码、Token与真正的凭据文件按用途选择模板；缺少的密码明确待补；再由独立会话按说明完成录入并核对实际使用入口。

公开材料仅含计数与问题说明，不含真实密码、Token、私钥或用户源文件路径。见[核对记录](evidence/ai-intake-synthetic-20261103/credential-visibility-followup.json)。

## 已实现的修复

Mac详情页现在同时显示信息中保存的凭据关联和凭据库指向该信息的关联；凭据页也显示被哪些资料引用。重复引用只显示一次。来自对方的关联标明修改入口，编辑时仍只保存本条资料自己管理的关联，避免一次普通保存复制或复活已移除的关系。不迁移数据库，也不改写现有资料和密钥。

动态凭据模板和随包Skill已补充：按实际认证材料选择密码、Token或文件；JSON/Markdown里的秘密不能只因来源扩展名就整份当文件交差；凭据直接关联实际服务器、服务或账号。明确账号未提供当前密码时准备主人补填，旧密码或哈希不能充当已验证的当前密码。个人Skill路由的说明已发布并通过Skillshare同步，具体格式仍由当前App查询。

验证包括35项关联和编辑回归、21项录入与内容回归、19项核心录入和模板回归，App及核心静态检查无问题。另从真实备份恢复到临时独立数据库，确认10个已有凭据关联的服务器或应用均能显示原凭据，47条信息、16条凭据和原有关系不变；此检查未读取生产Keychain。

代码检查通过不代表实际凭据整理已完成。安装统一新版后，继续由原独立聊天按照更新后的说明核对来源与库中凭据，提交修正和主人补填申请；保留已录入资料，不清空重录。#78/#79保持打开，待真实申请和主人补填结果确认后更新。
