## 实际用户流程

`native-ui-session-10` 使用构建内绑定的真实 broker、真实 Flutter runner、隔离 SQLCipher/DPAPI 库和独立编译 CLI，测试进程退出 0。假密码只在测试专用边界核对，生产 broker 不读回控件值。

- 批准前拒绝使用，接收器为空、没有输入操作；实际界面批准只建立许可，不立即填充。
- 第一个申请只批准一次，原期限内完成三次 Unicode 输入；中文、emoji、首尾空格均匹配，无 paste、剪贴板不变。重复操作 ID 返回原结果，不重放。
- 改变焦点后保存 unknown/focus_changed，阻止换新 ID 自动重填；经实际界面人工确认、清空并重新聚焦后可明确再用。人工确认没有改写旧结果或延长许可。
- 实际界面撤销后新操作拒绝；已完成的旧 ID 仍只返回原记录。
- 为验证重启，另建第二个请求并在真实界面批准，确认它在关闭前仍 available，没有输入。重开同一加密库、在同一端口启动新服务后，**保持原 CLI 进程仍存活**，其查询与使用均返回 unauthorized/session_required。保留 2 个请求、4 条操作，无许可复活。

因此整轮有两次批准：第一次证明多次使用，第二次专门证明活动许可在重启后失效。此前正常 WidgetsBinding 的 Win32/内置浏览器流程和失败均保留在[较早记录](issue35-native-user-flow.md)，不重标为本轮 testWidgets 结果。

## 辅助功能失败的定位

此前 `testWidgets` 默认先请求框架语义、随后外部 UIA 接入时出现 AV。新增不含资料库、凭据或审批组件的 MaterialApp 弹窗探针，在同样顺序下复现 `flutter_windows.dll+0x3c1ea`、`CreateRemoveReparentedNodesUpdate +186`、0xc0000005。dump 留在本机，不入库；只归档符号化元数据。内存仓储的实际审批组件在没有晚接 UIA 时通过。

控制组让真实 Windows/UIA 请求语义：初始框架/原生语义均 false，外部接入后均 true、根节点 0，弹窗打开/关闭通过。结合 SDK 源码，原因推断为原生桥建立前框架已缓存语义树，后续只发送增量时原生树不完整；引擎没有重编译或插桩，不能将内部树状态推断写成直接观测。上游[同函数报告](https://github.com/flutter/flutter/issues/175041)仅作参考，不声称根因完全相同或已修复 Flutter。

正式原生验收改为 Windows 驱动语义初始化，保留主动开启的显式诊断参数。交互期间语义确实为 true。结束时先卸载组件，严格核对句柄数量，只释放本轮新增的系统语义句柄；原测试框架末尾断言保持。3 项回归覆盖正常释放、额外应用句柄仍失败、既有系统句柄不被接管。**没有修改 SDK 或关闭生产辅助功能，也没有忽略应用句柄泄漏。**

`native-ui-session-09` 漏选新请求导致第二次批准失败，保持失败记录；第 10 轮通过实际导航和请求控件修正测试步骤后完整通过。

## 支持边界与后续
