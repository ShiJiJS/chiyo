## 新取得的真实系统事实

只读 `SHQueryUserNotificationState` 返回 HRESULT 0、状态 5；这是 Windows 定义的可接收通知状态，不等于已显示或已点击。[微软状态定义](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ne-shellapi-query_user_notification_state)

第五次有界探针（`native-01`，修复前的工作区诊断源码）只向 Shell 投递一次，记录 `sendAttempts:1`、`lastAccepted:true`、`shown:1`、`timedOut:2`、`clicked:0`、`idMismatch:0`。系统已发送显示回调，约六秒后终态回调到达；没有真实点击，60 秒截止后测试明确失败。该计数不冒充可见画面截图，也不能唯一解释此前四次缺少阶段记录的失败。Shell 事件的含义见[微软 Shell_NotifyIcon 文档](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shell_notifyiconw)。

Computer Use 的窗口/应用清单仍没有可点击的通知目标，未发送点击或键盘输入，随后 reset。临时 SQLCipher/DPAPI 库位于本次独立目录，结束后已删除；测试窗口退出，语义句柄 0→0。诊断采用已验证的 OS 请求语义方式，未关闭生产辅助功能。用户旧程序、资料库和系统通知设置未变。

## 复现与修复

旧队列以单个托盘 ID 接收所有通知回调。A 超时后开始 B，A 的第二次超时会被当作 B 的终态，再提前开始 C。新增 C++ 行为测试在旧实现编译成功、运行退出 1，验证了这一队列错误；它不证明历史缺失点击由此引起。

修复让每次发送携带独立的原生通知标识，并实际注册到 Shell。持久托盘入口与单次通知入口分开，单次入口使用隐藏图标状态；终态先退休该入口，再处理队列。队列和原生边界都核对回调标识，旧的超时、隐藏或点击不影响新请求。Windows VERSION_4 回调只暴露 16 位图标 ID，因此保留低区给托盘，在一次进程生命周期中使用其余 **61,440** 个发送标识，Reset/Explorer 重建均不重用；耗尽明确拒绝通知，不回绕为另一个请求，申请仍保留在收件箱。[微软图标及回调字段定义](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ns-shellapi-notifyicondataw)

这里只保证当前有效通知的回调对应其请求；已经终结、退休的通知回调被忽略，不将它映射到后续申请。没有声称提供通知中心的长期通知保存或应用已完全退出后的启动激活能力。
