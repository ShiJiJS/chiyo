## 来源与步骤

旧库由实际已交付0.4.0+8的`291801046f7d1e6e4217a4bc001ea714689855c5`
归档源码生成，42个Core/Storage库文件逐字节与原归档核对。归档SHA256
`7d775372e4fc710fcda55918c205a393724d9d8c794de911137575c79c491c0e`，
合成夹具SHA256 `159d9791b4c94f1302b41105ca272766fceb37f63c610c26a97f09159a8cc2d3`。
这是真实旧schema16/备份5，不是修改当前库的user_version冒充旧源。
固定合成数据库密钥由新QA夹具封装为当前用户DPAPI文件；不声称此文件来自旧版GUI，
没有打开真实用户资料或旧演示程序。

1. 旧源码创建1条1字段信息、1份字符串凭据、2条v1使用记录（1次已消费、1次未消费）、
   1条启动失败事实，并生成格式5独立加密备份及恢复密钥文件。确认实际schema16、格式5。
2. 为该虚构库的固定测试密钥创建DPAPI封装，此步骤不打开或迁移数据库。实际Release
   子进程仅使用专属LOCALAPPDATA，在原47125端口启动；独立AOT CLI可查询原目录身份。
   经新CLI正常退出后，先直接读取数据库版本（尚未由检查仓储打开），已为21。
   原信息值、凭据原文在QA进程内比较一致，只输出布尔值；两条使用记录仍为v1、
   消费次数1、未消费记录grant_revoked，启动事实1。DPAPI文件、原备份和恢复密钥原字节保持。
3. 复制已关闭的整个虚构库，仅在副本运行旧读取器。旧读取器返回
   `library_unavailable`，**会改动副本的旧版本标记**；不能把拒绝打开宣传为旧版只读或
   保证不写新库。源库哈希保持。新版实际程序能重新打开副本，恢复正确版本标记并保持
   原事实；源库也独立重开成功。因此升级后仍不能用旧版程序直接打开原库。
4. 启动另一独立空库，通过真正系统文件对话框分别选择旧加密备份与恢复密钥文件。
   原文没有送入聊天。界面预览显示格式5、1条信息、1份凭据/秘密版本、2条凭据使用历史、
   1条启动事实；明确旧格式无普通附件、不会恢复活动会话和许可。实际点击确认恢复，
   界面显示恢复成功、需重新申请，目标已非空不能覆盖或合并。
5. CLI目录核对恢复后原信息身份保持；正常退出后重新打开加密仓储，读取到实际schema21，
   信息及凭据原文、v1历史/次数/失效均一致。目标本机密钥不同于源测试密钥，原备份及
   恢复密钥字节保持。恢复的是过去事实，不给旧v1记录新增v2复用许可。

四个实际Release进程全部由同包CLI正常退出0，没有强制终止。三份虚构资料库及复制的
旧源测试材料已回收，47125无监听，Computer Use会话已reset。系统文件选择确认2次；
文件对话框作为所属窗口的原生模态画面返回，窗口清单没有单独列出。UIA元素缓存及
焦点文本在该工具中不可靠，实际采用所见截图中的文件名框/按钮；只输入已创建的虚构
文件路径，不读取或转述密钥值。观察回执是人工/Agent实际查看的记录，不是自动识图断言。
