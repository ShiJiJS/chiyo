# 修正审批状态筛选中的负数计数（#48）

2026-10-22，基于6e6088a，仅Mac分支。实际普通绑定Release的合成资料全部25条待处理，
切到已处理后却显示“全部0、待处理25、已处理-25”。在
[通知抑制的手动兜底](macos-notification-reuse.md)中发现，未将其误记为通知投递故障。
[失败回归、源码检查、源快照及摘要](evidence/macos-inbox-status-counts/verification.json)。

根因是InboxPage.total已应用状态筛选，而pendingCount采用搜索匹配、尚未按状态
筛选的范围。UI直接拿二者相减，混用了不同集合。现在InboxPage提供allCount，取
搜索匹配总数；全部/待处理/已处理三个标签用同一范围。total仍表示当前状态筛选
的总数，用于结果数和分页，不简单将负数钳制为0或修改原分页含义。

复用已有ProposalPage.allCount的相同计数约定；离线空页补零。这个模型仅供Owner
工作区使用，没有改变Agent协议、授权边界、数据库schema或持久资料。

新增完整InformationApp回归覆盖25条全待处理、切已处理/待处理、处理一条后24/1、
搜索到已处理一条时的1/0/1、切换状态后仍保持相同搜索范围计数，以及无匹配的0/0/0。
修正前Mac和Windows两种widget平台模式均失败/退出1；修正后两种模式、搜索/通知定位/
主题及默认键盘相关共11通过，Core工作区3通过。Core另核对240条请求的各状态分页总数
与allCount/pendingCount、精确搜索及空查询，避免只修显示而留下语义不一致。

完整四包严格分析与源码检查720通过/66条件跳过：Core285/6、CLI75/40、Storage159/18、
Desktop201/2。这是本机Mac上的源码/平台模式检查，不冒充Windows原生runner/CI。
检查完成时637项源码摘要已保存，用于后续固定源码整包核对；文档和生成文件不在该集合。

本轮修正后的计数使用自动回归验证，没有再发系统通知或声称新的原生计数截图通过。
4690e79固定安装和a458035候选ZIP尚不含此修正；后续整包及普通GUI验收仍需收口。
