## 原因证据与处理

只读取A所建合成项的ACL元数据，未修改它。解码系统生成的`Partitions`，仅有A的
`cdhash:<value>`，与A实际签名输出逐字节一致；B的不同CDHash不在该分区内
（完整值见原始签名输出和result）。
即便两版DR都使用同一证书leaf哈希及bundle identifier，这个额外分区仍绑定A。
这与本机两种路径下的实际拒绝一致；没有移除分区、加入新代码哈希、允许所有应用
或导出原数据库密钥来强行通过。

[Apple TN2206](https://developer.apple.com/library/archive/technotes/tn2206/_index.html)
说明Keychain与应用DR的跟踪关系，以及自签身份是否可用取决于具体子系统策略。
它是归档资料，不能代替本机当前系统额外ACL分区的实测。这里只报告这组采用生产
KeyStore的原生沙盒探针结果，不据此宣传任何证书/其他机器或Flutter最终包已通过。

因此暂不创建永久自签身份，不将它接入普通打包器。继续保留已允许的固定应用；
日常独立UI测试使用合成内存密钥，修复集中到后续完整候选再统一升级。若后续采用
其他有效签名身份，必须重新完成真实旧项、两版程序、旧库迁移和最终包验证。
当前ad-hoc条件下，不能承诺每次更新都免去系统决定，也不要求为本机预览增加付费
签名前提。#42保持4/5、#50保持2/6，整票均OPEN，未改变验收标准。
