# 九张 Windows 工单的执行约定

## 启动与恢复

1. 读取 AGENTS.md、本目录 README.md、progress.md、tickets.json 和当前 GitHub 工单/评论。持续目标已获用户启动，按当前用户最新授权接续。
2. 核对 Git 分支、提交和工作区，保留 progress.md 登记的环境准备改动及用户编辑。可使用开发分支 codex/windows-online，逐票提交；需要隔离并发编辑时采用独立工作区。
3. 按真实前置选择下一项，默认顺序为 2→3→4，之后 5/6/7，再 9/10，最后 11。默认由当前主 Agent 执行，不自动创建侧栏聊天或根据旧历史启用子 Agent。
4. 恢复时先核对进度、已有操作回执和登记的子进程，接续原工作；响应丢失不代表可以重复执行、重建身份或清掉原记录。

## 每张票怎么做

1. 在 progress.md 写当前票、要接通的正常入口及预期结果。
2. 沿用已有业务规则和平台实现完成改动，使用正式模板、文件驱动和加密库；按实际问题补必要检查。
3. 跑本票相关分析、测试与构建。失败先定位是产品、装配还是旧测试假设，修复后定向复验；代码缺陷不能随意挪到“用户回来以后”。
4. 全部本票完成条件满足后提交，记录提交号、命令、退出码、日志和明确未测范围。已通过的无关检查不反复重跑。
5. 回填 GitHub 并回读，满足本票定义才关闭。GitHub 暂不可用时留待回填记录并继续独立工作；不得用未检查的本地状态伪造远端完成。
6. 更新 progress.md 的当前结果、下一张票和首个具体动作，然后直接继续。不要每完成一张就结束整个目标、等用户说“继续”。

## NAS、资料与系统操作

- 直接对接现有 NAS 服务，不把 WSL、Docker 或另建服务列为本轮前置，不重新实现已完成的服务端。
- NAS 的现有资料保持。必要写入用明确标识、可追踪的合成资料；开发只清理自己创建的测试材料，不永久删除或恢复覆盖现有 NAS 资料库。备份恢复验证使用合成备份和独立空目标/已有测试能力。
- 用户管理身份与 Agent 设备身份分开，合成审批可由测试协调侧走正常用户接口；Agent 本身不能取得审批权。Token、控制证明及凭据材料不进入聊天、普通日志或版本库。
- 已有 Agent Info association 只复用原引用。若丢失，请求重新连接，不查文件或按聊天 ID 恢复。缺少连接或 NAS 暂不可用时，记录具体条件并继续不依赖它的代码和检查，不能将未验证的 NAS 流程标成通过。
- computer-use 已获准在必要时使用；正式安装和需要用户认证的操作仍最后集中。2026-11-10 用户允许用现有实际资料做验证、允许正常重启知予服务；不把这些授权扩大为永久删除或覆盖现有资料库。
- 沿用固定 gh/SSH/AWS 接收方式和版本要求。SSH 密码登录、前台密码填充、#105、手机及离线编辑不扩入这九票。
- 打包明确使用 -PackageOnly，避免旧默认逻辑自动安装。保留一个最新完整候选、摘要和必要故障证据，先正常退出所属测试进程再清理登记的可重建产物。
- 正式安装、全局 hooks/Skill 信任、系统认证、主分支合并或影响现有 NAS 服务的变更，在最终交接中列明并按用户当次指令执行。默认不使用付费托管 CI。

## 持续执行的停顿条件

普通实现选择、可逆修复和已有检查失败由 Agent 自行处理。需要用户身份/系统认证、改变已确认产品规则或环境确实无法继续时，保存证据及最小所需动作，再做其他独立工作。所有剩余工作都被外部条件挡住时，如实说明阻塞，不能报完成；若使用持续目标工具，遵守工具本身的状态、预算和阻塞规则。

## 最后交付

九张票均按自身完成条件审计，方案 11 给出同提交 Windows App、CLI、worker、helper、Skill 引用与说明的完整包；连续检查主要业务并修复遗漏。报告候选路径/提交/摘要、实际通过与未测范围及集中人工核对清单。

方案 11 的开发交付不自动表示正式安装或全部原生交互已完成。#104 的真实第二电脑交付条件全部满足后才关闭；#105 仍后置。必要的真实桌面操作在同版本候选上核对，不额外发布旧草案的交付票。
