Agent 遇到密码框后，知予怎样接着填写？

用户让 Agent“登录项目工作台”。Agent 打开页面，遇到了一个需要填写的密码框；密码保存在知予里。接下来，它要先弄清楚这是哪个页面、哪个输入框，再把目标与凭据使用申请交给知予。获批之后，知予才安排相应的填写代码执行。

这篇文章把整段交互连起来讲：Agent 怎样告诉知予“用哪份凭据、填到哪里”？知予怎样执行这次操作，又通过什么 API 找到输入框并送入文字？

本文按已确认的新设计讲解：统一使用 chiyo，网页批准限定到指定表单和字段，并加入 Chrome 页面填写。开发正在推进；下文命令为设计示例，最终参数以实现后的帮助为准。

先确定讨论范围

浏览器中的网页
例如网站登录页里的密码框，可以从页面元素和浏览器的控制入口入手。
普通桌面应用
例如桌面客户端的密码框，需要考虑应用向操作系统提供的控件信息与输入接口。

两类目标都要考虑 macOS 和 Windows。本文从 Agent 选择目标、提交请求讲到知予获准后操作网页或桌面应用；会展开影响目标选择的申请与授权信息，凭据如何加密存储则作为背景。

接下来怎么讲

  1. 先讲网页：确定页面和输入框 → 从知予的目录选出密码 → 提交申请并获得许可 → 发起填写。随后展开知予的内置填写模块怎样连接浏览器、发送具体操作。
  2. 再扩展到普通应用：看 Agent 怎样通过点击表达目标，辅助程序怎样通过系统查询控件，再把文字交给系统投递；具体调用处分别展开 Mac 与 Windows。
  3. 最后看各方的分工：Agent 选择目标，知予管理密码和批准；网页由内置模块操作，普通应用通过本机辅助程序输入。

01Agent 遇到登录页，先确定要填哪里

Agent 已经通过浏览器工具打开了项目工作台。工具返回页面内容或快照，Agent 结合“登录”这个任务，判断需要填写哪一个密码框。若页面同时有登录、注册或修改密码区域，Agent 还要结合区域标题、字段标签等信息，选择与登录任务对应的密码框。

然后，它把这个判断变成可定位的信息。浏览器把 HTML 组织成元素树（DOM）；Agent 可以让浏览器工具查询元素属性，确认选择器只指向所需的框。这一步得到的是目标位置，随后会用于向知予提交填写计划。

页面里的框已经找到了，怎样标明它在哪张页面？

刚才，Agent 已经在当前页面中确认：#password 唯一指向要填写的密码框。现在要把这个位置交给知予，还需要补上这张页面的标识，让知予的浏览器填写模块知道应该在哪张页面里使用这个选择器。

浏览器会为打开的页面分配标识，浏览器工具也可能提供便于操作的页面标记。Agent 把刚才查看、查询的那张页面所对应的标识一并交出，知予的浏览器填写模块才能回到同一张页面。标题和网址可以帮助核对，但同一网站能打开多个标签页，因此还需要能区分这些页面的标识。

下面分别看 ego 和 Chrome 怎样表示页面的位置。此处沿用 Agent 已经选定并正在操作的浏览器。

ego 怎样给页面标明位置？

目标位置已经确定，但密码由知予管理，Agent 需要先取得使用许可。它通过知予提供的命令行工具 chiyo，提交一份密码使用申请，由用户在知予 App 中审批。

申请获批后，Agent 才能按这条记录发起执行。下一节从执行命令开始，展开知予怎样实际操作浏览器。

一次申请包含多份密码时，怎样批准？

申请可以列出多条凭据，分别说明填哪个表单、哪个字段。用户可以只批准其中几项。某次操作同时需要 A 和 B，就要等 A、B 都获批；只使用 A 的独立操作，可以在 A 获批后执行。

03获批后，知予怎样实际填入密码？

现在申请 REQ-42 已获批准，接下来才执行。Agent 按申请编号发出命令：

chiyo fill run --request REQ-42 --json

知予取出申请里保存的目标，检查批准仍有效、密码版本仍相符，再把保存的目标和获准使用的密码交给内置的浏览器填写模块。这是知予中负责连接浏览器、查询页面和写入文字的代码；它拿到数据后，仍要检查实际目标，才能写入网页。

这次操作有自己的编号，例如 OP-42，用于后续查询结果。收到操作编号只表示可以追踪这次操作；下面继续看文字怎样真正进入网页。

知予的填写模块怎样接上指定的浏览器？

执行时，填写模块要通过连接向目标浏览器发送操作。申请阶段查询目标也使用这套连接方式；这里展开它具体怎样工作。ego 和 Chrome 提供的连接方式不同，下面分别看知予的填写模块怎样调用它们。

ego：由配套命令行工具建立连接

启动一个能连接 ego 的程序

ego 主程序提供了供配套工具接入的本机通信入口。知予的填写模块启动 ego-browser，指定 nodejs 模式；这个命令行工具负责接入入口，与正在运行的 ego 主程序建立连接。

ego-browser nodejs

知予的填写模块把要执行的 JavaScript 代码传给 ego-browser nodejs。ego 主程序收到后，会安排一个 Node.js 执行环境来运行脚本——也就是能执行 JavaScript、并能调用 ego 操作功能的环境。

连接建立后：知予的填写模块可以提交控制脚本，脚本的输出和执行结果也能沿原通道返回。网页和标签页仍由浏览器管理。

ego 的连接与脚本执行机制 ↗
Chrome：连接目标页面的消息地址

从页面列表取得地址，再建立连接

前面的申请已经指定 Chrome 的控制地址 http://127.0.0.1:9222。这个 Chrome 需要已开放供外部程序操作页面的入口，准备方式见第 1 节的展开说明。执行时，填写模块访问该入口的页面列表：

http://127.0.0.1:9222/json/list

地址中的 127.0.0.1 表示本机，9222 是这个入口使用的端口号，/json/list 表示查询页面列表。找到 Agent 选定的页面 A7C93D1E8B624F06B3D28AC572E4910F 后，取出该记录的 webSocketDebuggerUrl。这个字段就是用来连接此页面的消息地址。

{
  "id": "A7C93D1E8B624F06B3D28AC572E4910F",
  "url": "https://workspace.example/login",
  "webSocketDebuggerUrl":
    "ws://127.0.0.1:9222/devtools/page/A7C93D1E8B624F06B3D28AC572E4910F"

知予的填写模块连接这个地址，等待连接成功。这里使用 WebSocket：一种建立后可以持续双向收发消息的连接。

连接建立后：知予的填写模块通过这条连接发送命令，命令就交给页面 A7C93D1E8B624F06B3D28AC572E4910F 处理；浏览器的回复从同一连接返回。

上面分别得到“能提交 ego 控制脚本的通道”和“能向 Chrome 目标页面发送消息的通道”。本机地址、端口与页面编号用于说明对应关系。

连上浏览器后，要发送哪些操作？

连接建立后，知予还要告诉浏览器“执行哪段网页代码”。ego 和 Chrome 在这里使用同一套命令约定，叫 CDP（Chrome DevTools Protocol）：消息说明操作名称和参数，浏览器再返回回复。其中，Runtime.evaluate 表示让页面运行一段 JavaScript。

ego 的控制脚本通过 page.cdp() 发送这条命令；Chrome 由知予沿刚建立的 WebSocket 发送。两边先执行查询，再决定能否写入。

申请时保存的是当时的页面情况。在等待批准期间，页面可能跳转，登录表单也可能改变。因此，即使这是第一次执行，也要把现在的目标与申请时的记录比较，确认仍可按原申请填写。

下面先展开查询和判断，再说明写入动作。

先检查：页面现在仍然是预期的目标吗？

比较分两层：先确认还是申请时的浏览器和标签页，且网址一致；再在这张页面中找到唯一的 #login，确认其中只有一个符合条件的 #password，并把区域和字段的结构与申请时保存的记录比较。例如，申请时保存的是密码输入框，执行时同一位置变成普通文本框，就不能继续。即使编号仍叫 password，也不算通过检查。

例如，下面这次查询仍与申请记录一致，就可以进入写入步骤：

核对内容申请时保存执行时查到
页面ego 工作区 7 / 页面 p1
网址：workspace.example/login		仍是同一浏览器中的 7 / p1，网址相同
登录区域#login
包含账号框、密码框和登录按钮		#login 唯一，区域结构仍相符
密码字段区域内的 #password

Chrome 对应比较申请里保存的浏览器实例和标签页标识，其余区域、字段检查相同。若页面身份、区域结构或字段条件不符，就停止本次操作。

知予的填写模块先安排一次查询操作：读取页面现在的网址，并检查 #login 是否唯一、它里面的 #password 是否也唯一。查询使用的还是前面讲过的 DOM 方法；这里要解释的是它怎样被送到浏览器里执行。

ego：提交一段查询脚本

脚本选中页面，再请求页面执行查询

知予的填写模块调用 ego-browser nodejs，传入下面的脚本。脚本在 ego 安排的 Node.js 环境中运行。page 是代表 p1 页面的操作对象。

const task = await taskSpace(7);
const page = task.page('p1');

const queryCode = `({
  url: location.href,
  forms: document.querySelectorAll('#login').length,
  matches: document.querySelectorAll(
    '#login #password'
  ).length
})`;
const reply = await page.cdp('Runtime.evaluate', {
  expression: queryCode,
  returnByValue: true
});
const state = reply.result.value;

page.cdp() 把命令交给 p1 对应的页面。expression 放要执行的代码，returnByValue 要求带回查询值。因此 location 和 document 指向网页里的对象；返回的 state 留给控制脚本作判断。await 表示等待结果。

Chrome：发送一条查询消息

把查询代码放进消息，沿已建立的连接发送

Chrome 通过 WebSocket 接收同一条 Runtime.evaluate 命令。下面用 JSON——按“字段名：值”组织的文本——表达一次查询：

{
  "id": 1,
  "method": "Runtime.evaluate",
  "params": {
    "expression": "({url: location.href, forms: document.querySelectorAll('#login').length, matches: document.querySelectorAll('#login #password').length})",
    "returnByValue": true
  }
}

知予的填写模块把这段文本发送到上一步建立的 WebSocket。method 表示“执行页面代码”，expression 是代码内容；returnByValue 要求把查询到的值带回来。id 给这次查询编号，帮助对应回复。

浏览器返回现况，控制代码决定是否继续

两边都能从查询结果中取出下面几个值：

{
  "url": "https://workspace.example/login",
  "forms": 1,
  "matches": 1
}

控制代码把返回的网址与 Agent 提交的预期网址比较，并确认只匹配一个登录区域及其中的一个字段。网址不同，或者匹配数量不是 1，就停止这次填写。在 ego 例子中，判断写在刚才提交的控制脚本里；直接操作 Chrome 时，判断写在收取消息回复的知予的填写模块里。

上面的查询只展示网址和匹配数量。完整填写还要核对申请中保存的表单及字段信息，并检查密码框类型、是否可编辑等条件；仅凭网址相同、同名框唯一，还不足以确认是原先批准的目标。比较通过才进入写入步骤；无法确认一致时，知予停止这次操作。

同一份批准下再次填写，检查会省略吗？

不会。批准仍有效时，再次发起填写仍要检查浏览器、页面、网址及表单和字段。页面刷新后，只有页面身份和保存的结构信息仍符合时才能继续；换了标签页、表单发生变化或无法确认时就停止。这里的检查针对每次执行，第一次填写也一样。

检查通过后，把密码写入确认过的框

目标检查通过后，填写模块才把获准密码写入网页。下面用公开文字 hello 代表这次写入的密码，先对照它与目标的关系，再展开填写方法：

两种浏览器都执行同一段网页写入代码

知予把“再次检查目标”和“修改这个元素”放进同一次页面调用中。下面先看准备发送的写入代码节选；此时还没有发送。代码运行时，field 指向刚通过检查的 #login 内的 #password：

// 取出浏览器为 input 提供的 value 写入方法
const setValue = Object.getOwnPropertyDescriptor(
  HTMLInputElement.prototype, 'value'
).set;

// 把文字写入已经确认的这个元素
setValue.call(field, 'hello');
field.dispatchEvent(new Event('input', { bubbles: true }));
field.dispatchEvent(new Event('change', { bubbles: true }));

value 保存输入框当前的文字。setValue.call(field, 'hello') 调用浏览器原有的写入方法，把这个框的值设为 hello。后两行通知网页“输入内容发生了变化”，让网页处理相应更新；bubbles: true 让外层表单也能收到通知。

知予把完整的检查及写入代码保存为字符串 fillCode，再按下面两种方式之一发送。实际执行还会核对：收到代码的是否仍是刚才检查的那一版页面。无法确认是否已经写入时，知予报告“结果未知”。

04换成普通应用，怎样指定要填的框？

网页这条路径已经走通：Agent 指定页面与元素，知予核对许可，由内置填写模块通过浏览器入口操作网页。现在，把目标换成项目工作台的桌面客户端。凭据仍可从知予的目录选择，但怎样表达输入框的位置、通过什么入口操作它，需要重新考虑。

不同应用使用不同的界面技术，不能普遍沿用网页里的 HTML 选择器。操作系统提供了另一个共同入口：查询应用中的输入框、按钮等界面元素。这些元素称为控件；其中，当前接收键盘输入的控件具有输入焦点。

下面沿着一种具体方式展开：Agent 点中密码框，让它取得输入焦点；知予的辅助程序再向系统查询此刻的焦点控件，并向它送入文字。这条方式称为“本机焦点填充”。先看目标如何表达，再讲系统查询和输入调用。

点击怎样把 Agent 选中的框变成输入目标？

Agent 让桌面操作工具把目标窗口切到前台，再点击密码框。工具把点击交给操作系统，系统把鼠标操作送到对应窗口；应用处理点击后，通常会把输入焦点移到这个框。此后送给应用的键盘文字，就由它的输入处理逻辑交给焦点控件。

这次点击产生了一个可查询的桌面状态：“前台是项目工作台，焦点在密码框”。下图可切换账号框与密码框，观察这个状态如何变化。

为客户端提交一份密码使用申请

Agent 申请使用同一条密码记录 cred-workspace-01 第 1 版，用途是登录项目工作台客户端，允许范围是这个客户端应用。它通过知予的 chiyo 提交申请；--via focus 让知予根据当前前台应用确定申请对应的应用身份。

Agent 点中客户端的密码框后，在后台创建申请，避免操作终端时把焦点移走：

chiyo fill request \
  --via focus \
  --credential cred-workspace-01 --version 1 \
  --purpose "登录项目工作台客户端" --json

知予向系统查询此刻的前台应用和焦点控件，核对申请对应的应用及控件条件，并保存应用身份，返回待批准的申请 REQ-43。

这次查询不会把焦点锁住。系统焦点方式按执行时实际选中的密码框填写；它能核对所属应用，不能像网页选择器那样指定某个表单和字段。

等待用户审批客户端的使用申请

用户在知予 App 中核对申请的凭据、用途和应用范围，决定批准或拒绝。Agent 用 REQ-43 等待结果：

chiyo requests wait REQ-43 --timeout 60 --json

申请获批后，Agent 可以按这份许可发起执行。下一节展开实际操作。

有多个密码框时，哪个框会成为目标？

由 Agent 根据任务点中的那个框决定。目标查询只观察当时的状态，不预留焦点；批准记录也只限定应用，并未绑定其中某一个密码框。

因此，Agent 发起填写前必须确认实际焦点仍在预期位置。如果此时已移到同一应用的另一个合格密码框，辅助程序可能把后者捕获为目标。捕获后的变化检查，只能检查“是否仍是刚才捕获的控件”，不能替 Agent 判断任务原本想填哪个框。

这里的 --via focus 申请限定应用，不接受网页网址、表单或字段选择器；系统控件信息本身也不证明网页登录来源。

辅助程序怎样知道选中的是密码框？

应用会通过操作系统的辅助功能报告界面信息，例如有哪些输入框、哪个框正在接收键盘输入、它是不是密码框。常见的界面框架已经替标准控件提供了这些信息；自绘控件需要应用开发者补上。

辅助程序调用系统函数，询问“当前选中的是哪个框”。系统查询应用提供的信息，返回一个代表这个框的对象。代码把它放在 field 中，随后还能继续询问：“这个框是不是密码框？现在能不能编辑？”

苹果提供的这组查询功能简称 AX，微软提供的叫 UI Automation（UIA）。辅助程序能否使用它们，还要满足当前电脑的系统权限要求；知予批准使用密码，并不会替它取得系统权限。

准备好文字时，目标会不会已经变了？

从捕获控件到取得密码、准备发送，中间仍有时间间隔。用户或应用可能把焦点移到另一个框。如果输入接口按此刻的焦点投递，文字就可能落到新位置。

因此，辅助程序在实际发送前再次查询应用、窗口和焦点控件，与准备阶段捕获的目标比较。发现变化就停止；只有检查通过，才调用下一步的输入接口。

这个检查缩短了变化可能发生的间隔，但没有锁住桌面。检查完成到输入被处理之间，焦点仍可能变化。

查到这个框后，能直接修改它的内容吗？

有些控件开放了直接设值的能力。Mac 可以用 AXUIElementSetAttributeValue 设置允许写入的属性；Windows 可以对支持相应能力的控件调用 ValuePattern.SetValue。这类调用把“哪个控件、什么值”一起交给辅助功能机制，由应用负责这个控件的代码处理。
