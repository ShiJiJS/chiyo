Agent 需要密码或私钥时，知予怎样接着处理？

用户让 Agent“登录项目工作台”。Agent 打开页面，遇到了一个需要填写的密码框；密码保存在知予里。接下来，它要先弄清楚这是哪个页面、哪个输入框，再把目标与凭据使用申请交给知予。获批之后，知予才安排相应的填写代码执行。

这篇文章把整段交互连起来讲：Agent 怎样告诉知予“用哪份凭据、交给哪里”？知予怎样执行网页与应用填写，又怎样让程序使用凭据完成任务并返回结果？命令执行部分按单次命令、SSH 私钥登录、SSH 密码长连接三个场景展开。

命令中的页面、目标和操作编号均为示例。网页以普通 HTML 密码框为例；普通应用部分限定于通过兼容验证的原生密码控件。

先确定讨论范围

浏览器中的网页
例如网站登录页里的密码框，可以从页面元素和浏览器的控制入口入手。
普通桌面应用
例如桌面客户端的密码框，需要考虑应用向操作系统提供的控件信息与输入接口。
需要凭据的命令执行
例如用密码备份数据库、用私钥登录服务器，或在 SSH 长会话中连续操作同一个远端 Shell。已有能力与拟议接口会分别标明。

这些使用场景都要考虑 macOS 和 Windows。本文从 Agent 选择目标、提交请求讲到知予获准后填写网页、操作桌面应用或启动本机程序，再说明后续内置 SSH 认证与持续 Shell 的设计；会展开影响使用范围的申请与授权信息，凭据如何加密存储则作为背景。

接下来怎么讲

  1. 先讲网页：确定页面和输入框 → 从知予的目录选出密码 → 提交申请并获得许可 → 发起填写。随后展开知予的内置填写模块怎样连接浏览器、发送具体操作。
  2. 再扩展到普通应用：从应用的控件树取得固定目标编号，申请批准后再直接设值；查询控件和写值的 API 分别展开 Mac 与 Windows。
  3. 接着讲需要凭据的命令执行：先看一次启动完成备份，再看本机 SSH 使用私钥、远端运行 df -h，最后说明怎样按 SSH-7 连续调用同一个远端 Shell，保留 cd 和 export 的效果。

01Agent 遇到登录页，先确定要填哪里

Agent 已经通过浏览器工具打开了项目工作台。工具返回页面内容或快照，Agent 结合“登录”这个任务，判断需要填写哪一个密码框。若页面同时有登录、注册或修改密码区域，Agent 还要结合区域标题、字段标签等信息，选择与登录任务对应的密码框。

然后，它把这个判断变成可定位的信息。浏览器把 HTML 组织成元素树（DOM）；Agent 可以让浏览器工具查询元素属性，确认选择器只指向所需的框。这一步得到的是目标位置，随后会用于向知予提交填写计划。

页面里的框已经找到了，怎样标明它在哪张页面？

刚才，Agent 已经在当前页面中确认：#password 唯一指向要填写的密码框。现在要把这个位置交给知予，还需要补上这张页面的标识，让知予的浏览器填写模块知道应该在哪张页面里使用这个选择器。

浏览器会为打开的页面分配标识，浏览器工具也可能提供便于操作的页面标记。Agent 把刚才查看、查询的那张页面所对应的标识一并交出，知予的浏览器填写模块才能回到同一张页面。标题和网址可以帮助核对，但同一网站能打开多个标签页，因此还需要能区分这些页面的标识。

下面分别看 ego 和 Chrome 怎样表示页面的位置。此处沿用 Agent 已经选定并正在操作的浏览器。

ego 怎样给页面标明位置？

Agent 做一项任务时，可能同时打开登录页、帮助页等多个标签页。ego 可以把这项任务使用的标签页组织在同一个组里，这个组叫工作区（TaskSpace）。工作区有自己的编号；组内被工具管理的页面，又分别有 p1、p2 这样的标记。

02目标找到了，怎样向知予申请使用密码？

目标位置已经确定，但密码由知予管理，Agent 需要先取得使用许可。它继续通过 chiyo 提交一份密码使用申请，由用户在知予 App 中审批。

申请获批后，Agent 才能按这条记录发起执行。下一节从执行命令开始，展开知予怎样实际操作浏览器。

一次申请包含多份密码时，怎样批准？

申请可以列出多条凭据，分别说明填哪个表单、哪个字段。用户可以只批准其中几项。某次操作同时需要 A 和 B，就要等 A、B 都获批；只使用 A 的独立操作，可以在 A 获批后执行。

03获批后，知予怎样实际填入密码？

现在申请 REQ-42 已获批准，接下来才执行。Agent 按申请编号发出命令：

chiyo fill run --request REQ-42 --json

知予先检查批准仍有效、密码版本仍相符，再把申请里保存的目标交给内置的浏览器填写模块。这段代码负责连接浏览器、查询页面和写入文字；它先检查现在的页面和表单，检查通过后才会收到本次获准的密码并执行写入。

CLI 在首次发送执行请求前，为这次操作生成并保存编号，例如 OP-42，随后在命令回复中返回它，供 Agent 查询结果。收到操作编号只表示可以追踪这次操作；下面继续看文字怎样真正进入网页。

知予的填写模块怎样接上指定的浏览器？

执行时，填写模块要通过连接向目标浏览器发送操作。申请阶段查询目标也使用这套连接方式；这里展开它具体怎样工作。ego 和 Chrome 提供的连接方式不同，下面分别看知予的填写模块怎样调用它们。

ego：由配套命令行工具建立连接

启动一个能连接 ego 的程序

ego 主程序提供了供配套工具接入的本机通信入口。知予的填写模块启动 ego-browser，指定 nodejs 模式；这个命令行工具负责接入入口，与正在运行的 ego 主程序建立连接。

ego-browser nodejs

知予的填写模块把要执行的 JavaScript 代码传给 ego-browser nodejs。ego 主程序收到后，会安排一个 Node.js 执行环境来运行脚本——也就是能执行 JavaScript、并能调用 ego 操作功能的环境。

连接建立后：知予的填写模块可以提交控制脚本，脚本的输出和执行结果也能沿原通道返回。网页和标签页仍由浏览器管理。

Chrome：连接目标页面的消息地址

从页面列表取得地址，再建立连接

前面的申请已经指定 Chrome 的控制地址 http://127.0.0.1:9222。这个 Chrome 需要已开放供外部程序操作页面的入口，准备方式见第 1 节的展开说明。执行时，填写模块访问该入口的页面列表：

http://127.0.0.1:9222/json/list

地址中的 127.0.0.1 表示本机，9222 是这个入口使用的端口号，/json/list 表示查询页面列表。找到 Agent 选定的页面 A7C93D1E8B624F06B3D28AC572E4910F 后，取出该记录的 webSocketDebuggerUrl。这个字段就是用来连接此页面的消息地址。

{

连接建立后：知予的填写模块通过这条连接发送命令，命令就交给页面 A7C93D1E8B624F06B3D28AC572E4910F 处理；浏览器的回复从同一连接返回。

连上浏览器后，要发送哪些操作？

连接建立后，知予还要告诉浏览器“执行哪段网页代码”。软件提供给其他程序调用的操作接口，称为 API：调用者按约定指定操作和参数，软件处理后返回结果。浏览器也提供这样的接口。

ego 和 Chrome 在这里使用同一套命令约定，叫 CDP（Chrome DevTools Protocol）：消息说明操作名称和参数，浏览器再返回回复。其中，Runtime.evaluate 表示让页面运行一段 JavaScript。

ego 的控制脚本通过 page.cdp() 发送这条命令；Chrome 由知予沿刚建立的 WebSocket 发送。两边先执行查询，再决定能否写入。

申请时保存的是当时的页面情况。在等待批准期间，页面可能跳转，登录表单也可能改变。因此，即使这是第一次执行，也要把现在的目标与申请时的记录比较，确认仍可按原申请填写。

下面先展开查询和判断，再说明写入动作。

先检查：页面现在仍然是预期的目标吗？

比较分两层：先确认还是申请时的浏览器和标签页，且网址一致；再在这张页面中找到唯一的 #login，确认其中只有一个符合条件的 #password，并把区域和字段的结构与申请时保存的记录比较。例如，申请时保存的是密码输入框，执行时同一位置变成普通文本框，就不能继续。即使编号仍叫 password，也不算通过检查。

例如，下面这次查询仍与申请记录一致，就可以进入写入步骤：

核对内容申请时保存执行时查到
页面ego 工作区 7 / 页面 p1
网址：workspace.example/login		仍是同一浏览器中的 7 / p1，网址相同
登录区域#login
包含账号框、密码框和登录按钮		#login 唯一，区域结构仍相符
密码字段区域内的 #password
type=password		该区域内唯一匹配
仍为可编辑的密码框

Chrome 对应比较申请里保存的浏览器实例和标签页标识，其余区域、字段检查相同。若页面身份、区域结构或字段条件不符，就停止本次操作。

知予的填写模块先安排一次查询操作：读取页面现在的网址，并检查 #login 是否唯一、它里面的 #password 是否也唯一。查询使用的还是前面讲过的 DOM 方法；这里要解释的是它怎样被送到浏览器里执行。

ego：提交一段查询脚本

脚本选中页面，再请求页面执行查询

知予的填写模块调用 ego-browser nodejs，传入下面的脚本。脚本在 ego 安排的 Node.js 环境中运行。page 是代表 p1 页面的操作对象。

const task = await taskSpace(7);
const page = task.page('p1');

const queryCode = `({
  url: location.href,
  forms: document.querySelectorAll('#login').length,
  matches: document.querySelectorAll(
    '#login #password'
  ).length
})`;
const reply = await page.cdp('Runtime.evaluate', {
  expression: queryCode,
  returnByValue: true
});
const state = reply.result.value;

page.cdp() 把命令交给 p1 对应的页面。expression 放要执行的代码，returnByValue 要求带回查询值。因此 location 和 document 指向网页里的对象；返回的 state 留给控制脚本作判断。await 表示等待结果。

Chrome：发送一条查询消息

把查询代码放进消息，沿已建立的连接发送

Chrome 通过 WebSocket 接收同一条 Runtime.evaluate 命令。下面用 JSON——按“字段名：值”组织的文本——表达一次查询：

{
  "id": 1,
  "method": "Runtime.evaluate",
  "params": {
    "expression": "({url: location.href, forms: document.querySelectorAll('#login').length, matches: document.querySelectorAll('#login #password').length})",
    "returnByValue": true
  }
}

知予的填写模块把这段文本发送到上一步建立的 WebSocket。method 表示“执行页面代码”，expression 是代码内容；returnByValue 要求把查询到的值带回来。id 给这次查询编号，帮助对应回复。

浏览器返回现况，控制代码决定是否继续

两边都能从查询结果中取出下面几个值：

{
  "url": "https://workspace.example/login",
  "forms": 1,
  "matches": 1
}

控制代码把返回的网址与 Agent 提交的预期网址比较，并确认只匹配一个登录区域及其中的一个字段。网址不同，或者匹配数量不是 1，就停止这次填写。在 ego 例子中，判断写在刚才提交的控制脚本里；直接操作 Chrome 时，判断写在收取消息回复的知予的填写模块里。

同一份批准下再次填写，检查会省略吗？

不会。批准仍有效时，再次发起填写仍要检查浏览器、页面、网址及表单和字段。页面刷新后，只有页面身份和保存的结构信息仍符合时才能继续；换了标签页、表单发生变化或无法确认时就停止。这里的检查针对每次执行，第一次填写也一样。

04换成普通应用，怎样固定要填的密码框？

网页的做法已经讲清：Agent 找到页面和元素，把它们写进申请；获批后，知予通过浏览器接口填写。接下来把场景换成一个压缩工具：Agent 打开了需要密码的窗口，希望把知予保存的密码填进去，同时让用户继续使用电脑上的其他窗口。

普通应用中的输入框、按钮等界面元素称为控件。对于支持的原生控件，操作系统提供了查询和设值的方法：辅助程序先取得代表那个控件的对象，之后把对象和文字一起交给系统，指定“修改这个框”。用户此刻在哪个窗口打字，不参与目标选择。

这里先解决目标从哪里来、怎样交给 Agent，再申请使用密码。Mac 与 Windows 的申请过程相同，查询控件和最后写值所用的系统 API 分别展开。

网页与原生，怎样把目标交给知予？

网页的目标定位信息已由 Agent 从浏览器工具取得；原生先取得目标列表，再用选中的目标编号申请。

应用标识只选择查询范围，知予还会核对实际运行程序的身份。

知予怎样把查询交给辅助程序？

现在已经看到了 Agent 会收到的目标列表，接下来展开它怎样产生。fill targets 只查询可操作控件：chiyo 把查询交给本机知予 App，App 再把查询消息交给辅助程序。辅助程序查询目标应用并返回控件说明。

凭据使用申请仍由后面的 fill request 提交，由知予保存、交用户审批，并在实际执行前检查许可。辅助程序负责查询、核验控件和获批后的设值，不创建或批准申请。

05获批后，怎样向固定控件写入密码？

现在已有一份获批申请，以及辅助程序保存的具体控件对象。Agent 发起执行；知予需要先确认许可和控件都仍有效，再取得密码交给辅助程序，最后调用系统设值接口。

chiyo fill run --request REQ-43 --json

CLI 同样在发送执行请求前生成并保存操作编号，例如 OP-43，再通过命令回复返回它，供后续查询。申请编号 REQ-43 指向用户批准的记录，操作编号则对应这一次具体填写。

先复核原来的控件，再取得获准密码

知予检查原聊天和设备、批准期限、凭据版本以及操作是否已经执行。辅助程序则用保存的对象复核：应用进程是否仍是原来的那次运行、窗口与字段是否仍存在、控件是否仍可写，窗口上下文是否仍符合原申请。

切换到邮件或编辑器，不会改变已选定的目标。需要重新确认目标的一个具体场景是：Agent 找到解压密码弹窗后，你点了“取消”关闭它，稍后又重新尝试解压，应用再次弹出密码窗口。原来保存的是第一次弹窗里的控件引用；新弹窗即使标题、位置相同，也不能继续沿用旧目标，需要重新查询并取得对应批准。辅助程序重启同样会使原引用失效。

Agent 如何获取填写结果？

辅助程序完成设值调用后，把结果沿前面建立的私有连接返回知予 App。知予再通过刚才的 chiyo fill run 命令回复，把本次操作编号 OP-43 和填写结果交给 Agent。回复说明执行情况，不包含密码原文。

Agent 后续还可以用同一个操作编号查询结果；如果刚才没有收到执行回复，也先查询这次操作。这条命令只查询，不会再次填写：

chiyo operations show OP-43 --json

对于本例的原生密码框，sent 表示系统设值调用已被接受；明确没有写入时，知予返回拒绝结果和原因。如果写值期间失联，无法确定有没有写入，就返回 unknown，Agent 不能据此自动重试。

收到 sent 后，Agent 还要检查应用界面。填写密码和点击“确定”是两个动作，需要提交时再另行操作；压缩包是否成功解压，则要根据应用的后续结果判断。

哪些普通应用可以这样填写？

需要应用提供可查询、可设值的原生密码控件，还要通过实际兼容验证。Mac 使用 AppKit 的标准安全文本框是可行路径，但不能推广到全部 AppKit 应用；首批产品兼容配置仅包括已验证的系统归档实用工具、系统版本和窗口结构。Windows 验证覆盖 Win32、WinForms、WPF 原生密码控件，以及真实 7-Zip 场景。

内嵌网页、WKWebView 和 Electron 暂不通过这条原生路径填写。浏览器继续用前面讲过的专用接口。即使外观相同，系统返回的控件能力和应用处理设值的方式也可能不同。

最后一次检查和实际设值不是一个能锁住目标 App 的事务：应用仍可能在两者之间关闭窗口或改变业务状态。后台填写解决的是固定控件和避免依赖全局焦点，不能保证任意应用的所有业务变化都可由外部检测。

06需要使用凭据执行命令时，知予怎样处理？

前面讲的是把密码填进网页或应用。还有一些任务没有等待填写的输入框：用户希望 Agent 备份数据库，或登录服务器检查项目。这时需要让程序使用密码、Token 或私钥完成操作，再把执行结果交给 Agent。

下面按三种使用场景展开：单次命令、SSH 私钥登录、SSH 密码长连接。先看一次启动就能完成的任务，再看私钥如何用于远端命令，最后说明用密码登录后怎样保留连接与同一个 Shell，让后续命令延续前面的目录和变量。

使用场景例子本节要讲清的区别
一、单次命令用数据库密码完成一次备份凭据交给指定程序；本次程序结束，操作就结束
二、SSH 私钥登录用已保存的私钥执行 df -h私钥交给本机 SSH，命令在服务器上运行
三、SSH 密码长连接登录后依次执行 cd、pwd、git status知予保留同一个远端 Shell，后续通过会话编号继续执行

“私钥／密码”区分登录方式，“单次／长会话”区分执行状态是否继续保留。因此下面是三种常见场景，不是三种互斥的底层模式；后续的 SSH 长会话也可以使用私钥登录。

当前能力与后续替代方向

已有的 chiyo exec 可以把凭据交给程序的标准输入、指定环境变量或受管文件，再管理程序执行；现有 ssh_identity 专用路径支持私钥登录。通用执行配合 Expect 脚本，也已经能够用 SSH 密码登录：知予把密码注入 Expect，脚本启动 SSH，识别密码提示后发送密码，执行完这一批命令就退出。

后续专用 SSH 功能将替代由 Agent 临时编写 Expect 脚本的用法，统一处理私钥或密码登录，并提供持续会话。继续复用知予现有的审批、凭据交付和执行记录；通用单次命令能力保留。下面的 chiyo ssh 命令是拟议接口，内置密码适配和持续 Shell 管理仍待实现，当前脚本路径尚未因这份设计而停用。

一单次命令把凭据交给程序，完成本次任务

单次命令支持三种凭据交付方式：标准输入、环境变量和受管临时文件。选择哪一种，取决于目标程序从哪里读取凭据；它们使用同一套申请、批准和执行流程。

标准输入：程序从输入管道读取密码

例如，用户要备份项目数据库。假设本机工具 /opt/example/db-backup 支持 --password-stdin：它从标准输入读取完整密码，收到输入结束信号后开始备份。这是教学工具及参数，不代表系统自带它。

Agent 用 chiyo exec request 提交计划，写明程序、参数、工作目录，以及凭据 cred-db-01 第 1 版应交给 stdin。凭据编号指向知予保存的密码，计划里没有真实密码。下面先申请，再在用户批准后执行；REQ-45 代表申请返回的示例编号：

chiyo exec request \
  --credential cred-db-01 --version 1 \
  --via stdin \
  --executable /opt/example/db-backup \
  --cwd /opt/example/work \
  --arg=--password-stdin \
  --purpose "备份项目数据库"

# REQ-45 获得用户批准后
chiyo exec run --request REQ-45

知予的本机执行组件检查程序身份与批准范围，启动备份程序，通过它的标准输入交付密码。程序用密码连接数据库并写出备份；知予收集输出与退出状态，供 Agent 按本次操作编号查询。Agent 结合这些结果判断备份是否成功，不能把“操作已登记”或“进程已启动”当成备份成功。

知予交付凭据的原始 UTF-8 字节后关闭这条输入管道，表示输入结束，不自动添加换行。只有程序确实从标准输入读取凭据时才用这种方式；看到“请输入密码”的提示，并不能说明它读取的是标准输入，例如 SSH 登录密码就需要专门的认证适配。

环境变量：启动程序时，把凭据放进指定变量

假设本机工具 /opt/example/project-tool 用来查询项目状态，约定从环境变量 API_TOKEN 读取服务 Token。这也是教学工具；实际使用时要填写已安装程序的真实路径、变量名和工作目录。

Agent 怎样申请：选择知予保存的 Token cred-token-01 第 1 版，声明接收方式为 env、变量名为 API_TOKEN，并提供程序及参数。申请里只有凭据引用，没有 Token 原文：

chiyo exec request \
  --credential cred-token-01 --version 1 \
  --via env --variable API_TOKEN \
  --executable /opt/example/project-tool \
  --cwd /opt/example/work \
  --arg status \
  --purpose "查询项目状态"

# 假设返回 REQ-47；用户批准后执行
chiyo exec run --request REQ-47

知予怎样注入：执行时先检查原批准、程序身份和凭据版本，再取出获准 Token，放进本次启动程序的环境映射中，变量名就是 API_TOKEN。知予带着这份环境启动 project-tool status，所以程序启动后就能读取该变量。Agent 不需要先读取 Token，也不需要在自己的终端执行 export API_TOKEN=...。

程序怎样拿到：如果这个教学工具用 Python 编写，内部读取变量的片段就是：

import os

token = os.environ["API_TOKEN"]
# 用 token 向项目服务认证，再查询状态；不打印 token。

这里的 token 是目标程序运行时拿到的真实值，供程序自己使用；Agent 只拿到程序输出的项目状态和执行结果。API_TOKEN 是程序约定的变量名，cred-token-01 是知予中的凭据编号，两者通过申请对应起来，不能把凭据编号本身当成 Token。

这份环境交给由知予启动的程序，不会修改 Agent 当前 Shell 或系统的全局环境变量。程序创建的子进程可能继承它；获批程序也能读取真实凭据，因此这种交付方式仍须信任接收程序，不能当作阻止恶意程序泄露密码的隔离措施。

临时文件：程序接收路径，再读取文件内容

另一些程序只支持从文件读取密码。假设前面的备份工具还支持 --password-file，后面必须跟密码文件路径。Agent 仍然引用 cred-db-01，并让知予把受管文件路径插入参数列表：

chiyo exec request \
  --credential cred-db-01 --version 1 \
  --via file --file-argument 1 \
  --executable /opt/example/db-backup \
  --cwd /opt/example/work \
  --arg=--password-file \
  --purpose "通过密码文件备份项目数据库"

# 假设返回 REQ-48；用户批准后执行
chiyo exec run --request REQ-48

参数位置从 0 开始：位置 0 是 --password-file，位置 1 留给知予生成的路径。获批执行时，知予把凭据写入私有受管临时文件，再按下面的形状启动程序：

db-backup --password-file <知予分配的文件路径>

程序收到的是路径，再自行打开文件读取密码。Agent 不需要取出密码或自己创建明文文件；实际路径由知予分配，不是把占位文字直接当作路径。确认整个受管进程树结束后，知予再清理该文件。若程序要求从环境变量获得文件路径，也可使用 --via file --variable 变量名；这种情况下变量里放的是路径，和上面的 env 直接交付 Token 不同。

三种方式都要匹配程序的真实接口。知予根据申请中的凭据引用与接收位置交付材料，不会随意把密码替换进普通命令字符串。

这里的“单次”指一次程序启动，可以运行较久，也可以在内部完成多步工作。它不会为下一次启动保留同一个 Shell。程序运行中可查询输出；确认相关受管进程结束后，再清理临时材料。同一聊天可以在批准仍有效且范围相符时提交下一次独立操作，不必每次重新审批。

二SSH 私钥登录本机使用私钥，远端执行命令

现在换成“查看测试服务器还剩多少磁盘空间”。本例使用知予保存的文件凭据“测试服务器 SSH 私钥”，编号 cred-ssh-01、第 1 版，登录 ops@ops.example.net，执行 df -h。服务器已配置对应公钥，私钥须能用于非交互认证；地址和编号都是教学示例。

Agent 提交什么，用户批准什么？

Agent 提交启动计划，说明本机 SSH 程序、服务器与账号、远端命令，以及私钥应放在 -i 参数之后。申请只带私钥引用，不带原文。用户批准申请 REQ-44 后，当前聊天才可以在批准的主机、程序和凭据接收范围内使用这一版私钥。

同一聊天可以在许可有效时继续提交其他远端命令，每次都有独立操作编号。例如 OP-44 标记本次提交，避免重试把同一次操作启动两遍。许可复用不等于保留 SSH 连接，也不表示知予会判断后续每条命令是否安全；换主机、程序身份或私钥接收位置，需要重新批准。

私钥怎样交给 SSH，结果怎样回来？

发起执行后，知予复核批准、凭据版本、主机信任和程序身份，将获准私钥写入受管临时文件，把路径放到 ssh -i 后面，再由本机执行程序启动并跟踪 SSH。简化后相当于：

ssh -i <知予分配的私钥文件> ops@ops.example.net df -h

SSH 在本机读取私钥用于认证，不把私钥文件上传到服务器。认证成功后，远端 SSH 服务以账号 ops 启动 df -h；命令在服务器上运行。输出、错误和结束状态沿连接回到本机 SSH，再由知予收集，供 Agent 查询。

私钥证明登录者的身份，服务器也需要证明自己的身份。现有专用路径使用事先确认的 known_hosts 主机信任记录，严格核对服务器的主机密钥；陌生或不匹配的密钥不能在执行时自动接受。这条路径使用非交互私钥认证，不弹出登录密码提示。

知予返回本次执行编号 EX-44，Agent 用它查询状态和输出。例如 df -h 的 / 挂载点一行显示 Avail 为 20G，且执行正常结束，才能据此回答剩余空间约为 20G。查询输出不会重启 SSH；结果未知时应查原操作，不能直接换编号重跑。

确认本次受管进程树结束后，知予才清理临时私钥和配套配置。一条 CLI 调用结束不代表 SSH 已结束。现有许可的撤销会阻止新使用，但不会自动终止已经运行的远端任务。

现有私钥调用与后续入口

当前私钥专用路径使用 ssh_identity 和已有的 request-use、run-use、execution-status、execution-output 协议。查询本次执行可表示为：

{"command":"execution-status","executionId":"EX-44"}
{"command":"execution-output","executionId":"EX-44","cursor":0,"limit":16}

这些是现有协议的请求示例；后续计划以专用 SSH 入口统一表达私钥与密码认证。此处展示现有机制，不意味着私钥只能用于单次命令；需要持续工作时，私钥登录也可接入下一节的长会话设计。

三SSH 密码长连接登录一次，后面的命令继续执行

用户希望 Agent 进入服务器的项目目录，再检查仓库状态。若每次重新登录并启动 Shell，上一条 cd 的效果就不会自动延续。为此，知予需要在登录后保留 SSH 连接和同一个远端 Shell，并返回一个会话编号。

Agent 使用密码凭据 cred-ssh-password-01 申请连接 ops@ops.example.net，说明端口、登录账号、认证方式、凭据版本、用途和预期操作。用户批准后再打开会话。以下是拟议接口：

# 申请长会话，返回 REQ-46，等待用户批准
chiyo ssh request \
  --credential cred-ssh-password-01 \
  --version 1 --auth password \
  --host ops.example.net --port 22 \
  --user ops \
  --purpose "检查服务器项目"

# 获批后登录，会话准备就绪时返回 SSH-7
chiyo ssh open --request REQ-46

密码怎样用于登录？

打开会话时，知予核对批准与服务器身份，再由内置认证组件把本次获准密码交给 SSH 客户端完成登录。Agent 只提交凭据编号；正常流程不把密码放进命令参数、普通日志或返回结果。

后续不再要求 Agent 自己写“等待密码提示、发送密码”的 Expect 脚本。内置组件承担登录适配，知予的持续执行组件负责登录后的连接和 Shell。私钥登录也可以进入同一套会话管理；具体密码认证接口在本节末尾的补充说明中展开。

会话编号怎样让 cd 的效果保留下来？

准备就绪后，知予返回 SSH-7，表示它保存的这条连接与远端 Shell。这个编号不包含密码，也不能单凭编号取得权限；每次后续调用仍要核对原聊天和有效批准。

本机执行组件持续运行，不随一条 CLI 调用结束。第一次 run 把 cd /srv/project 送入那个 Shell，改变其当前目录；第二次 run 把 pwd 送入同一个 Shell，所以输出 /srv/project；第三次 git status 继续在该目录中执行。

export 设置的环境变量也能延续。例如先执行 export PROJECT_ENV=staging，后续在该会话执行 printenv PROJECT_ENV，仍得到 staging。只复用网络连接不够，还必须保留原来的 Shell；每条命令另开 Shell 就不能保留这些状态。后续命令仍由知予代执行，Agent 根据结果决定下一步，无须接管密码或 SSH 进程。

Agent 怎样取得每条命令的结果，又怎样结束会话？

SSH-7 标识整个会话，每条命令另有独立操作编号，分别记录是否送达、输出、完成状态与退出码。一个会话先按顺序执行，前一条未结束时，不把下一条误送给正在运行的程序。知予需要可靠区分每条命令的开始和结束，不能把 Shell 提示符或整个 SSH 进程的退出当成每条命令的完成信号；这部分执行约定仍待实现。

Agent 完成任务后调用拟议的 chiyo ssh close --session SSH-7。如果断线或本机组件丢失原连接，原会话应标为失效或结果未知，不自动重发命令，也不悄悄新建 Shell 沿用旧编号，因为目录和变量可能已经丢失。关闭连接不能保证所有远端程序都停止。

第一阶段围绕 cd、export、文件查询和普通脚本设计。vim、top 或 sudo 再次询问密码等交互，需要额外的终端、输入和中断能力，不能算作已经支持。撤销、到期或聊天结束后拒绝新命令；运行中任务、空闲连接如何中断与回收，仍需在实现前确定。

密码认证的实现方向

一个实现方向是沿用系统 OpenSSH，通过 ASKPASS 调用知予随包的认证辅助程序，再由它经本机私有通道取得本次获准密码并交给 SSH。这里只用它说明密码请求怎样交给本机组件；私有交付通道、进程核验和 Mac／Windows 兼容性仍待实现与验证。登录适配与后续 Shell 管理是两部分工作。

无论采用哪种场景，实际连接与执行都发生在 Agent 所在电脑。资料库存放在 NAS 时，NAS 上的知予服务负责保存资料、审批和授权核对，本机组件负责启动程序、连接目标服务器与收取输出。正常流程不返回凭据原文，仍不代表能防止恶意 Agent 或获批程序主动泄露凭据，安全边界见下一章。

07知予能防止恶意 Agent 窃取密码吗？

不能保证。无论网页、原生填写还是程序执行，知予都可以避免凭据原文通过正常操作命令的回复进入 Agent 上下文，减少正常协作中的意外暴露；这不等于 Agent 无法从其他途径取得密码或私钥。SSH 程序会实际读取私钥；知予也不能保证它对具备相应权限的其他本机进程隐藏。

填写后，密码已经进入目标页面或应用。如果 Agent 还具备足够的页面脚本执行或应用控制能力，仍可能从目标一侧取得内容。例如，网页密码框显示为圆点，并不阻止有相应权限的页面脚本读取其值；原生密码控件是否可被其他工具读取，则取决于系统、应用和工具能力。

恶意 Agent 也可能谎报任务用途，诱导用户批准向不符合真实意图的页面或应用填写。前文的身份核验、固定目标与审批仍然有效，但它们不能判断 Agent 的真实意图，也不能约束 Agent 通过其他工具进行的操作。

因此，应使用可以信任的 Agent，并核对申请中的用途与目标。通俗地说，这更接近“防君子不防小人”：它能降低正常流程中的密码暴露风险，不能作为隔离恶意 Agent 的安全保证。
