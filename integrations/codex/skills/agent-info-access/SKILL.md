# 信息授权软件使用说明

资料保存在当前选择的本地库或服务器；App 管理和审批；CLI 查询、提交申请和交付获准内容。本 Skill 说明使用方法，具体模板、字段格式、说明和例子由当前服务的插件提供。安装 Skill、连接会话和提交申请均不代表获准；批准录入也不授予读取或使用许可。

## 本机运行与当前会话

使用本机接入描述已核对的同版本 `info-codex`、`info-codex-hook` 与 worker。运行包末尾给出的程序路径或本机描述的 `cliPath` 是执行入口；程序和说明不匹配时报告需要更新接入材料。安装、更新、启用或信任 hooks 属于配置操作，本流程不自动改动。

首次连接或核对连接方式时，先读[资料库连接与命令调用](references/remote-connection.md)。CLI 默认发现 App 已确认的当前库配置；运行包指定 `Connection profile` 时使用该准确路径。配置只用于接入，审批仍在 App；本地模式需要 App 在后台运行，关闭窗口仍可接收申请，显式退出后服务停止；服务器模式不要求 App 持续运行。按末尾的 `Session state directory` 使用对应状态目录（若提供）。只把配置路径传给程序，不读取或输出配置内容，不查找 App 的管理 Token。

1. 优先使用当前聊天 SessionStart 已提供的私密 `association`。它是能力引用，不能打印、写入命令行、普通日志、提交或无关聊天；不能按聊天 ID 搜索或恢复关联文件，也不读取 Codex 的登录文件或聊天记录。
2. 本次任务需要使用软件时，聊天连接由 Agent 自行处理，无需用户另行确认或复述连接口令。已有有效关联直接复用；首次连接、关联引用丢失，或 `session-check` 确认原会话已无效时，执行同包 `info-codex-hook --connect` 创建新的**未授权会话**。运行包指定 `Connection profile` 时传入 `--connection`，否则自动发现；按指定值传入 `--state-root`（若有）。一次恢复最多新建一次，失败报告具体原因。新连接不继承旧申请、批准范围或期限；业务申请仍在 App 审批。被拒绝、撤销或到期的访问不能靠重连自动重提。
3. CLI 每次读取独立 stdin JSON，附本聊天的私密关联与 `command`。用执行工具的独立 stdin，或 Node／Python 的子进程管道传入；不要把整个 JSON 拼成 shell 命令、here-string 或 argv。工具不能安全传 stdin 时说明限制并停止私密访问。
4. 子进程 `CODEX_THREAD_ID` 必须是当前聊天标识。Node REPL 不继承时，从当前工具的 `nodeRepl.requestMeta.threadId` 设置，保留本机正常环境；聊天标识只作误用检查，不能代替实际关联。
5. 先查 `capabilities`。按服务实际提供的入口执行；服务不可用时保留已有请求标识，恢复后先查原状态。没有所需能力时说明需要更新或暂缓该项，不把别的格式当作已完成。

## 按本次任务选择流程

- 用户给文件、资料或要求新增／修改：按下节整理并提交录入申请。
- 申请阅读已保存的信息：走“申请资料”，文件字段再读 [普通附件交付](references/information-files.md)。
- 使用 Token、私钥、凭据文件执行命令或本机填充：先读 [凭据使用](references/credential-use.md)。这是使用已保存凭据，不是将凭据原文录成普通资料。
- 调整目录和标签：走“整理分类”。定位原始 infos 资料库则使用 infos Skill。

## 提交主题和来源

新版运行包需要 `submission-metadata.v1`。每次申请填写实际 `purpose`；新增、修改、删除和整理提案还填写一句 `title`，例如“补齐 NAS 应用清单”“更新校园网服务器配置”。标题说明本次要做什么，条数和资料类型由 App 另外显示。标题、Agent 名称、聊天标识各最多200字，用途最多2000字；这些说明中不放密码、Token、私钥或资料正文。

同包 `info-codex` 自动提供 Codex 名称和当前聊天标识；其他 Agent 以实际名称填写 `agentName`。通用 CLI 在 `session` 中提供 `chatLabel`、`externalChatId`，每次申请提供 `agentName`；也可在单次申请明确提供当前聊天的 `externalChatId`。它们只用于展示来源，实际授权仍由私密会话证明决定。

模板例子中的名称、聊天标识和主题都是虚构的：复用其 `items`／`update` 结构，替换成当前任务的主题和来源。`invalid_submission_metadata` 时按 `fieldErrors` 补齐原提交，不通过改名或换聊天取得旧许可。随包程序 `--help` 可在未连接时查看字段和示例；旧服务器不支持时报告需要更新。

## 整理、按模板录入和修改

用户指定的文件与资料是本次来源范围。自行判断名称、用途、分类、关联、条目数量和版本关系，不要求用户逐条指挥怎样建资料。已有资料的私有值若不在用户给定来源中，先取得正常读取授权；缺失事实保留未知，不猜填。

录入前阅读[来源整理与文件例子](references/information-file-intake.md)，先判断哪些是长期事实、独立原件、设备配置或无需重复保存的过程内容。正文写最终准确内容，申请原因简短解释本次变化；纠错替换错误说法，过程由修改历史记录。已有内容准确且没有新增事实时，不创建提案。

先查 `catalog`、`credential-catalog` 和 `directory-list`，核对已有对象、凭据与完整目录树（包括空目录、完整路径和同级顺序）；`complete:true` 才能当作目录已查全。目录可查不等于正文获准读取，也不授予移动、删除或新建目录的权限。旧服务没有完整目录查询时，明确说明限制，不声称已经排除重复目录。

1. 调用 `plugin-list`、`template-list`，从启用的模板中选择，再用 `template-read` 读取完整 `definition`、`inputLimits`、`relationInput`、`updateInput` 和 `submissionExample`；涉及普通文件时再读返回的 `fileInput`。每个模板的字段含义、必填项、格式、填写说明和虚构例子以本次查询为准。插件安装、更新、启停或移除后重新查询；不在 Skill 或 CLI 之外另存模板清单。
2. 没有合适模板或模板缺填写说明／例子时，说明这份材料需要什么格式，暂缓这一项。其他资料按自身审批和引用情况处理。新增或安装插件由用户决定，不能为了录入自行造插件。
3. 名称写实际对象，描述写简短用途；应用用软件名，独立部署用位置区分，设备专属配置另建合适资料并关联应用。目录按内容用途选择，参考已有同类资料的位置，模板类型不等于目录；修改默认保留原目录，调整位置时在提案中明确提出。私有事实放模板值中。地址、端口等结构字段填简短值；长说明放模板声明的正文，按声明选择 plain／markdown 等格式。公开名称、用途和普通字段不放凭据原文或整理过程。
4. 同一材料的前后修订作为历史版本；用途不同的材料分别建资料，例如两个投递方向。先完整提取有用信息；来源原件有独立保管、交付或修订价值时，再按当前文件模板建独立资料并关联，多处使用同一原件时复用。已提取完整且没有独立用途的来源不再附带保存。文件必须绑定模板声明的文件字段，不通过额外字段挂整份来源。版本以来源证据判断，不按文件名相似就合并。
5. 新增使用 `import-submit`。按查询返回的 `submissionExample` 结构填写 `items`，保留所选 `templateId`、`templateVersion`、`templateDigest`，真实值放 `values`；按上节填写本次主题和来源。可建议 `suggestedDirectory`、`suggestedTags`，它们只在用户批准并具备入库条件后应用。不要再用 `suggestedTemplate` 提示加平面文字来代替按模板保存。
6. 一份提案是一次完整提交和整体保存，不能按条目勾选部分入库。将需要一起新增的相关资料组织在同一提案；全部必填字段、密码和文件齐全后，由用户核对并一次保存。需要关联已入库内容时用公开目录中的准确 ID；同批待录入内容用稳定的 `itemKey`，由软件一起建立关联。跨提案再加同一会话中的 `proposalId`，但不能把它作为日常拆分用户一次操作的办法；未解决的引用会使整份等待。查询 `import-status` 可取得服务生成的 key。用户填写密码不另加一次密码审批；整份保存仍不授予AI使用许可。
7. 修改已有资料仍使用 `update-submit`，提供准确 `itemId` 与当前 `baseVersion`。按模板修改时同时提供模板三个标识和**完整 values**；先从获准来源取得现有文字值，明确保留或修改每个字段，已有文件按查询返回的 `retainFileValue` 明确保留。省略字段会报错，不意味着清空。只补文件的修改按文件录入说明，不要求重填无关正文。修改可关联待录入普通资料，须给目标 `proposalId` 与 `itemKey`。用户看前后变化再批准，等待期间原资料保持不变。
8. 只改明确字段且保留原含义时，也可用原有 `changes` 协议：`correct` 提供 `fieldId`、`value`；`add` 提供新 `field`；`replace` 明确更换字段含义；`remove` 明确删除。字段含 `name`、`description`、`value`、`kind`。此格式不与模板 values 混用；新增或替换的字段不会继承旧授权。
9. 保存返回的 `proposalId`，用 `import-status` 或 `update-status` 查**原提案**。等待审批时继续独立工作，不因等待、进程退出或超时重发。首次提交没有取得 proposalId 时报告收件结果尚未确认，先核对现有提案，不反复换内容提交。入库后逐项核对正式名称、类型、目录、版本和必要关联；有用来源信息都有去向，才报告整理完成。删除或清理仍走本次获准的管理流程，原始来源不在默认清理范围内。

状态决定下一步：

| 状态 | 行动与能报告的结果 |
| --- | --- |
| `pending` | 已提交，等待用户审批；尚未保存 |
| `approved_awaiting_admission`／条目 `approved` | 用户已批准，仍在等待关联；不能报告已入库或开始读取 |
| `needs_attention` | 核对引用或模板问题；保留这份申请，不自动拒绝依赖它的资料 |
| `confirmed`／条目 `admitted` | 核对返回的正式资料 ID 和版本后报告入库；读取仍须另行申请 |
| `rejected` | 停止该申请；不自动新建另一份绕过决定 |
| `conflicted` | 原资料版本已变，先读取当前获准内容，再准备新的修改与审批 |

修复待审批内容用 `import-revise`（`proposalId`、当前 `version`、保留 key 的 `items`）或 `update-revise`（`proposalId`、当前 `version`、修订的 `update`）。修订会清除相应旧批准，需要重新审批。`template_changed`、`template_unavailable` 或 `template_missing` 时先查询当前模板，再修订，不能悄悄降为通用资料或丢字段。

## 录入密码、Token 与凭据文件

先核对服务具备 `credential-import.v1`，从动态模板中选择 `recordKind` 为 `credential` 的格式，读其 `credentialInput` 与 `submissionExamples`，按其中的结构用 `import-submit` 提交。具体模板 ID 和材料格式以当前查询为准，不把凭据原文放进 `values`、普通字段、普通附件或公开名称。

- 尚未实际看到的人设账号密码由用户在 App 提案内填写；密码管理器生成后设为登录密码的也如此。选用户补填的分支，不让用户把密码发到聊天，不为录入特意先读取密码。
- 已从用户指定资料实际看到的凭据原文，由 Agent 直接填写并说明可能已经进入上下文；人设密码、来源不明的密码也适用，不让用户重复填写。API Key、Token 等其他字符串凭据同样由 Agent 填，明确已接触。
- 整份私钥、会话等凭据文件，把用户给定的文件路径放进模板例子的 `filePath`，交给 CLI 直接提交。不必读取原文，不要求用户再次选择；程序读文件不代表 AI 已经看过。只有确实看过原文时才标记已接触。不要将文件内容打印或转成聊天中的 Base64。

先判断认证时真正需要的是密码、Token还是一份文件，再选择动态模板。JSON、Markdown是来源的容器格式，里面记载的密码和Token仍分别属于字符串凭据；只有认证程序本身需要整份文件时才选文件形式。可另行保留来源原件，但“原件已保管”不代表其中的登录凭据已经整理完成。对于按上述规则应由Agent录入的凭据原文，可用本机命令在内存中读取明确字段并通过stdin提交，值不必输出到聊天；CLI不承担各软件配置字段的提取协议。Agent字符串入口的暴露提示按模板要求填写。

只知道 SSH 用户名和端口，或只知道一个账号，并不能确定需要密码；认证方式未知时保留未知，不凭空创建待填密码。确认来源采用密码、Token、私钥或外部身份登录后，再选对应模板。

每项凭据直接关联到它用于登录或访问的服务器、应用或账号，来源说明文档可以另加关联。按来源区分网页登录密码、API Token和SSH私钥等不同用途；用户名或登录邮箱按动态模板返回的账号位置填写，并直接关联实际使用它的服务；用途说明保持简短，不把账号和整理过程混成一段说明。来源明确采用密码登录却未提供当前密码时，提交用户补填分支并说明缺少哪项，缺少的密码由用户在提案中填写，与整份内容一次保存；不要把未知密码省略后报告完成。只有旧密码或密码哈希时，同样说明当前可登录密码尚缺，不能冒充已经验证有效。

为每次录入意图指定唯一 `operationId` 并保留，通信不确定时用 `import-status` 携原 `operationId` 找回提案，或查询已返回的原提案ID；同编号改变内容会报冲突，不能通过换编号重做未知结果。凭据文件由 CLI 有限读取后进入加密提案，源文件失效或材料为空时不能入库；以返回的限制为准。用户在提案中补填后按整份保存规则处理，状态与回执不返回密码或凭据内容。没有专用能力时暂缓，不能退回普通文字录入。凭据入库不授予使用许可。

## 申请资料

1. `catalog` 只返回公开元数据。选择本次需要的准确字段，用一次 `request` 提供 `purpose`、`fields`（`itemId`、`fieldId`）和稳定的 `operationId`，保留 `requestId`。收件不确定时先用 `request-status` 按原 operationId 核对，不换编号重发。
2. `status` 或 `wait` 查询同一申请；等待超时不重复申请。
3. 获批后 `claim` 核对用户最终选择和到期时间。文字字段用 `read` 提供 `requestId`、`itemId`、`fieldId`；文件按附件参考交付。独立 CLI 进程会私下领取同一许可，不因此重新批准或延长期限。
4. `denied`、`expired`、`cancelled`、`revoked`、`unauthorized` 时停止原访问。新的字段或条目需要新的申请；撤销不能追回已经披露的内容。

## 整理分类

使用同一会话的 `organize-request` 提供本次主题、用途、来源和候选 `itemIds`，保留 `taskId`；用户在 App 审批，不要求用户手动建立任务。通过 `organize-wait` 或 `organize-status` 查询原任务。

`active` 时调用 `organize-metadata`，只用最终获批 ID、版本、目录和标签，按用户目标整理。`organize-submit` 提供完整期望分类和标签；没有变化时提交空 changes 完成任务。此批准同时允许限定范围的元数据读取与分类改动，不再二次审批，也不授予私有值读取或正文修改。

结果不确定先查原状态；已完成、拒绝、撤销、到期、冲突或未授权时停止原任务。存储失败且任务仍 active 时，仅在原有效期内重试同一方案。旧版 proposed 结果仍须用户确认，不能当成新版自动应用。

## 子 Agent 与会话结束

只有任务本来需要同根子 Agent 时才委托。父会话用 `delegate` 提供自己的关联和准确 `childChatId`，把返回的私密 `privateAssociation` 直接放入该子会话的私密任务上下文；子会话用自己的 CODEX_THREAD_ID。它只共享已批准范围和原有效条件（限时截止或根聊天结束），不扩大授权。子会话缺证明时向父会话请求委托，不按父聊天 ID 查找证明。

startup、clear、fork 创建新的未授权关联；resume、compact 只保留已有引用。真实根 SessionEnd 结束它和子会话；普通 CLI 退出、子 Agent 完成、切换聊天不等于根会话结束。结束通知未送达时报告尚未确认，由用户在 App 撤销。服务器普通重启保留原有效许可和原到期时间，不恢复已结束或撤销的许可。

用户要求正常退出软件或已授权更换测试版时，同包 `info`／`info.exe app status` 查询，再 `app quit`。Mac 只控制同包实例，指定 PID 也不能选择另一目录；退出失败或超时先查原实例，不强杀。服务端版关闭 App 不结束服务器上的授权；需要停止某次访问时使用根会话结束通知或由用户在 App 撤销。

示例均为虚构；真实任务只处理本次用户指定资料。配置安装与信任状态应按实际客户端观察，不把受控测试当作所有客户端生命周期已验证。
