# 来源整理与普通文件录入

先对照已有获准内容整理事实与用途，再选模板。以下是判断例子，具体字段和提交格式一律查询当前 App；例子不是固定模板或目录清单。

| 来源情形 | 应整理出的结果 |
| --- | --- |
| 一份汇总 Markdown 介绍两台服务器及各自服务 | 提取设备、服务入口和必要关联。信息已完整覆盖、来源没有独立用途时，不再保存整篇汇总或另建“整理记录”。未覆盖的有用事实放合适字段或资料；缺模板则建议格式并暂缓相关项。 |
| 一份须保管或交付的证明原件，被多处资料使用 | 建一条独立文件资料并关联；已有同一原件则复用，不在每条资料下重复附原件。插件本身声明的业务文件字段仍按模板填写。 |
| 同一方向简历的真实修订，以及另一方向简历 | 前者一条资料保留多个版本，后者独立一条。用文内修订信息、文件名和来源说明判断先后；证据不足保留未知，不按提交次序或修改时间编造版本。相同原文副本不冒充修订。 |
| 同一软件分别部署在云主机与校园网 | 分别命名为“WireGuard 云主机”“WireGuard 校园网”，描述写隧道用途，关联各自服务器和凭据。不能因软件同名就合并部署，也不用“某某出口”代替软件名。 |
| 一个同步服务包含 Mac 专属目录与设置 | 应用保存服务入口、用途和部署位置；Mac 配置用合适资料单独保存并关联。不同设备的配置分别整理，不编造未提供的平台配置。若每台设备本身各运行独立实例，可分别保留部署。 |
| Telegram 连接资料和一份资源投递流程 | 连接入口和凭据属于应用及凭据；已明确由业务 Skill 及其配置维护的投递步骤和频道参数，不再重复存一份文档。其他独立有用配置仍可保留。仅凭名称不能判断重复；维护位置不明确时先核实。 |
| 已有资料中的部署主机写错 | 申请读取必要内容后，提修改申请，正文直接改为正确主机并保留其他正确字段、凭据身份及关联；修改原因说明改什么，不在正文追加“此前误判、某日更正”。 |
| 来源与已有资料相同，或聊天里只是试探未来计划 | 前者核对后无需提案；后者只有用户明确要求保存时，才按计划或记录用途整理。真实业务历史、设备配置和用户要求的记录继续保留。 |

目录按内容用途选择，先参考完整目录树及已有同类资料。外部平台连接也可以属于应用，并非只有自托管软件才是应用。新增、修改和清理的理由写在提案说明，长期正文只放最终有用内容；真正有用途的历史不一概删除。

## 文件提交与版本

先从 `doctor` 返回的 capabilities 确认包含 `information-file-upload.v1`，通过 `templates show/examples` 读取所选模板本次返回的 `fileInput`、限制与 `submissionExample`。普通文件也由用户批准后入库；文件上传成功只是收件，不是入库，也不授予 AI 读取许可。

按动态例子把用户给定路径交给 CLI。模板文件值绑定相应附件 key，具体结构以查询为准；本机路径、文件 Base64 与整段原文不写进普通文字字段或公开说明。无需用户在 App 重选。为各版本填写可理解的说明，明确选择哪份是当前原文；App 分配的版本号只表示保存次序，不代表来源材料的新旧。已保管材料的历史原文长期保留。

普通文件也走 `proposals check` 和 `proposals submit`。CLI 在提交前保存稳定的 operationId、来源和文件摘要。首次提交没有收到结果时，用 `operations show/retry` 携原编号找原提案，或用 `proposals show` 查询已知编号；不要换编号重复创建。兼容入口的单独上传结果不明时，按原上传 operationId 用 `import-file-status` 核对，不将上传成功冒充入库。缺文件、超限、模板变化或原文已不可用时，修复具体问题再提交，不能把普通文本称为原文备份。

给已有资料添加文件或新版本，先通过 `doctor` 确认 `information-file-update.v1`，读取动态返回的 `fileInput` 和 `fileUpdateExamples`。从公开目录确认准确资料、当前版本及现有文件字段，依据用户来源选择目标；内容相似不足以认定可以覆盖。新增文件必须绑定模板声明的文件字段；独立原件建文件资料再关联，已有附件加版本使用查询中的例子，只补历史稿时保留原当前文件。只改文件无需读取、重填无关正文；同时改正文时按模板的完整修改格式，明确保留已有文件。用户可查看原当前文件和新交原文，再批准；原资料变化后重新核对并审批，不能自动换目标。

私钥、登录会话等证明身份的文件使用凭据模板和凭据录入流程。只有上传能力而没有修改能力的旧运行包，暂缓已有资料的文件修改。
